01 / 快速结论

先记住这几句

  • 用户要的是 Jesse Vincent 与 Prime Radiant 的 AI 编程技能库 obra/superpowers。它和 Dex Horthy 的四门模型、非官方插件 factory-gates、以及其它同名项目不是一回事。
  • 当前可核对版本是 v7.0.2，annotated tag 指到 main 提交 22f0b463e7a5e579904dd6211a520321035526f7。本报告只讨论这一快照，不以 2025 年 10 月首发博文的旧流程当现行机制。
  • 它真正卖的是过程：先弄清要什么和为什么，写出设计并等人批准，再把决定写成可执行计划；实施时走 TDD，用子代理逐任务评审，或在同一会话里便宜地做完再终审；最后把合并或开 PR 的选择交还给人。
  • 技能正文里的 MUST、铁律、红旗表，是写给模型看的描述约束。真正会失败退出的，主要是 SDD 辅助脚本（指错仓库、没有提交、任务解析失败）。会话启动 hook 会注入 using-superpowers。Windows 未找到可用 bash 时才静默跳过注入；Unix 可回退到 zsh，只有 bash 和 zsh 都不可用时才以退出码 0 跳过。
  • README 仍写「设计批准后先建 worktree」「2–5 分钟任务、完整代码」。更具体的技能正文已经改成：批准设计后只调用 writing-plans，worktree 放到执行阶段并先征求同意，计划写接口和测试断言而不是整份实现。发生冲突时以更具体的技能正文为准，并在后文标出差异。
  • 对手机 WebRTC：它能管信令状态、重试策略、统计字段和测试是否先失败；不能代替真机弱网、芯片差异和实验室音质。单测全绿，不等于「弱网可用」。

03 / 范围

它解决什么，不解决什么

它试图解决的

编码代理一上来就写代码、写完却测的是已经存在的行为、一次会话里把计划忘光又重做、以及把合并、推送这些不可逆动作悄悄做掉。Superpowers 用一组会互相调用的技能，把「问清楚 → 写设计 → 等人批 → 写计划 → 选执行法 → 隔离工作区 → 红绿测试 → 评审 → 交还选择」变成默认路径。README L308–L324

对已经走偏的会话，它还提供 diagnosing-superpowers：按投诉类型读转录、给带行号的证据，而不是凭印象总结。

它明确不解决的

  • 不代替判断。 用户指令可以覆盖技能。对方说跳过提问，头脑风暴的门就一起撤掉。using-superpowers L63–L65brainstorming L269–L283
  • 不保证模型一定遵守。 没有编译器在写第一行产品代码前拦住它。接受测试「我们做个 react todo list，应先触发头脑风暴」是维护者对集成的要求，不是你仓库里的技术锁。AGENTS.md L82–L96
  • 不提供领域实现。 15 项里没有 WebRTC、Android 音频或芯片平台技能。领域知识仍要来自你的代码、规格和实验室。
  • 不创造真机证据。 完成门要求「有当次命令输出」，但输出是什么，取决于计划里写了什么命令。没有实验室步骤，它不能证明音质或弱网体验。verification-before-completion L14–L35
  • 不默认帮你改这个上游仓库或对外发布。 贡献指南对代理 PR 极严，拒绝率被写成 94%。本报告只读公开快照，不提交、不安装、不运行其脚本。

06 / 机制精读

触发、计划、执行、测试与评审，实际怎么咬合

触发与优先级：先过程，后实现

using-superpowers 把规则写得很硬：相关技能必须在任何回应或行动之前调用，包括澄清问题和查看文件。若还没做过头脑风暴就进入 plan mode，先调用 brainstorming。然后要宣布 “Using [skill] to [purpose]”，并精确按技能执行。using-superpowers L18–L24 多个技能同时适用时，过程技能在前：要做新东西，先头脑风暴；要修 bug，先系统调试，再进入实现或领域技能。using-superpowers L26–L31「这只是个简单问题」「我先看看代码」都被写成应停下的红旗。

这仍然是第 2 层描述约束。1% 规则 using-superpowers L10–L15 靠的是劝说式措辞——写作技能甚至把这类写法当成纪律手段来教——而不是权限系统。反例很直接：宿主没注入、模型选择忽略、或对方说「别问了直接改」，流程就会从中断开。前两个是遵守失败，第三个是规则允许的覆盖。

规划：问为什么、批准设计、计划里只留下实施者不能独自决定的事

brainstorming 的描述把自己绑在「任何创造性工作」上，软件内外都算。brainstorming L1–L3 v7 重建后再经 7.0.1、7.0.2 调整：先看已有材料和代码；只在答案会改变成品、且现有材料没有答案时才提问；还没说为什么，就先问为什么，而且是开放问题，不给选项；有可列举的选择时，才摆出方案并推荐一个。过程性事项（写到哪里、要不要再查）由模型自己决定并告诉对方。brainstorming L101–L107 发布说明附带了内部对话评测数字，那是作者实验，不是本报告复现。

真正的门在 HARD-GATE：设计文档（小改动用短文档，项目用完整文档）被批准前，不能写产品代码、脚手架、装依赖、建项目或调用实施技能；阅读和探索可以。两个例外：对方跳过提问，则技能结束、门一并撤掉；对方同意的 spike 可以做，但必须标成一次性，留下它要重新过门。批准之后，下一步只调用 writing-plans。brainstorming L269–L283 项目级文档在交给人之前，会先让一个「将来的建造者」子代理挑还要问的问题（没有子代理就自己扮演）。

计划技能把读者设定成「没见过这份规格和代码库的工程师」：他一旦知道接口和测试，就能写出惯用代码，但不能猜你已经做的决定。于是计划要锁定文件、名称、签名、规格里的值和证明任务完成的测试。writing-plans L140–L161 任务不再按「几分钟」切，而是按「自带测试周期、值得新评审者挡一次」来切。writing-plans L34–L41 计划如果比代码还长，就被看成把程序抄了一遍；「TBD」「加上适当校验」则是相反的失败。交出去后，若对方还没指定执行法，技能会说明代价并推荐一种：SDD 更完整但每个任务和每次评审都要新上下文；Native 更便宜，由当前会话做完，最后用最强模型做一次整分支评审。writing-plans L179–L204

视觉伴侣是可选浏览器页，用来展示草稿和对比，不是默认模式。启用时会在本机起服务器，URL 带会话 key；README 写明，默认会从 Prime Radiant 网站加载带版本号的 logo，可用 SUPERPOWERS_DISABLE_TELEMETRY 等变量关闭。README L398–L400 本报告没有启动该服务器。

执行与协作：两种走法共用账本，停下来的理由只有四种

两种执行技能都会先调用 using-git-worktrees 做或确认隔离工作区，并写明：未经明确同意，不要在 main/master 上直接开工。worktree 技能自己会先问，并优先用宿主原生工具，避免 git worktree add 留下宿主看不见的目录。using-git-worktrees L41–L45using-git-worktrees L51–L57

一旦开始执行，默认连续做完，不为「要不要继续」停顿。可以停的只有四种：不可逆或破坏性操作；安全敏感动作；规范要求先问的工作区外副作用（合并、推到共享分支、发布）；以及计划烂到每条路都是猜。其余冲突由控制器按「规格为权威、计划是它的论证」自行裁决，并写成 Ruling: 决定 — 理由 — 错了会付出什么。subagent-driven-development L17–L31 压缩后，真实发生过的最贵失败是：控制器忘掉进度，把已经做完的任务整段重派。所以进度写在 .superpowers/sdd/ 下该计划自己的 progress.md，并写明压缩后以账本和 git log 为准，不要相信自己的记忆。subagent-driven-development L108–L128 两种执行模式共用这套目录，中途可以换执行者。

SDD 把每个任务交给新鲜实施者：先用脚本抽出 brief，只把 brief 路径、与前文相关的接口、以及报告路径交给它，不要把整份计划和会话历史贴进去。实施者被禁止再派子代理，尤其禁止自己找评审。implementer-prompt.md L50–L60 必须显式指定模型，否则会继承最贵的会话模型。计划文本已经包含完整待写代码时，才允许用最便宜模型做「誊写加测试」——这是对计划内容的条件句，并不能让 README 那句「完整代码」重新变成现行要求。subagent-driven-development L140–L170 同一时刻不能并行派多个实施者。subagent-driven-development L235–L236 评审包必须用任务开始时记下的 BASE，而不是 HEAD~1，否则多提交任务会被悄悄截断。subagent-driven-development L243

修复环最多五轮：1–3 轮尽量接着原来的实施者；4–5 轮换更强模型的新鲜实施者；每轮都做范围受限的再审。封顶后控制器必须把未关问题写入账本，禁止悄悄丢掉。fix-loop.md L21–L77 终审只有一轮修复波，残项同样记裁决，并在收尾时交给人看。final-review.md L18–L31 Native 模式少掉了逐任务外审，改用 TDD、账本和一次终审来补；没有子代理时，技能要求明白写出这是更弱的自审。executing-plans L8–L18executing-plans L255–L260

v7.0.2 把辅助脚本改成「在当前工作区对应的仓库上运行」，并要求用绝对路径从项目工作树调用。以前从技能目录启动，会打到插件自己的文件；以前在仓库外运行，还可能把工作区写进插件缓存。现在这类错误会以退出码 2 失败。这是少数真正的技术强制。RELEASE-NOTES L3–L48 本文只读了脚本，没有执行。

测试与评审：看见失败、看见套件、看见当次输出

TDD 技能的铁律是「没有先失败的测试，就没有产品代码」。已经写出来的实现要删掉，不能留作参考。test-driven-development L31–L45 循环仍是红—验失败—绿—验通过—重构。验绿色时，「其它测试」指项目套件，不是只跑你新增的那个文件。test-driven-development L185–L193 一次性原型、生成代码和配置文件要先征得对方同意才能豁免。test-driven-development L24–L28 好测试附件要求：先命名这个测试要抓住哪一种生产破坏，并尽量打真实行为；用被测代码计算期望、或只断言源码里有某一行，都算失败写法。writing-good-tests.md L11–L25

一处内部张力要说清：实施者模板写的是 “Write tests (following TDD if task says to)”。implementer-prompt.md L34–L37 这比 TDD 技能的「总是如此」、也比 Native 执行「在 setup 就加载 TDD 技能」更松。若计划步骤写漏了红绿顺序，实施者可能按较松的模板走。这不是我推断出的隐式特性，而是两份原文并排可见的差异；落地时应以更严的 TDD 技能为准，并在计划步骤里把红绿写死。

verification-before-completion 把「完成」锁到当次消息里的命令输出：没跑、没读、只靠「应该过了」或「代理说成功」，都算没有证据。verification-before-completion L14–L35 它依然不能把 npm test 升级成「通话在弱网下可接受」。

评审技能要求把 Critical 立刻修好、Important 在继续之前修好。通用示例里还出现了 HEAD~1。requesting-code-review L26–L29 执行技能已经把这个写法标成会截断多提交任务的错误。发生冲突时，按执行技能的 BASE..HEAD 规则。收尾技能则要求：套件绿了才出示菜单；合并、开 PR 或保持原样由人挑；本地合并后还要再跑测试。finishing-a-development-branch L14–L82 这些都是工作区外副作用，报告只转述，不执行。

07 / 假设案例

手机 WebRTC：弱网卡死后的恢复，会怎样被这套流程接住

以下是为手机终端 / WebRTC 工程师构造的端到端假设，用来对照机制，不是实测记录。没有在真机、芯片平台或业务仓库里安装或运行 Superpowers，也没有声称某次通话被它修好。

假设现场反馈是：部分机型在弱 LTE 下通话会先卡死再无法恢复，需要应用层在 ICE 失败后重启，必要时降级编码，并给实验室一个隐藏的统计导出开关。若只对代理说「加个 ICE 重启」，当前技能希望先把它当作创造性工作：进入 brainstorming，而不是直接改 PeerConnection。

按 v7.0.2 的问法，第一件事通常不是方案菜单，而是为什么现在要做：是某次版本回归、某家运营商网络、还是实验室指标没过？已有代码和协议文档里能找到的，不应再问一遍。真正会改变成品的问题可能包括：只做应用层 restartIce()，还是允许整次重新协商；失败阈值按秒还是按 ICE 状态；编码降级是否动到现有 SDP 策略；统计导出是工程菜单还是日志。平台、语言、既有媒体栈，若对方只谈结果，应由模型给出默认并标明「这是我的决定，不是你点头同意的」。

设计文档应把反目标写清楚：本次不承诺改善 3A 音质，不承诺统一所有芯片平台的恢复率，不把单测通过写成「弱网可用」。建造者检查若还问「哪家调制解调器要先验收」，这属于会改变范围的问题，应送回给人，而不是悄悄限定成某一平台。人批准后，才写计划。

一份克制的计划会把可测行为拆成带接口的任务，例如：ICE 状态到重启动作的纯函数；重试与放弃；编码降级的协商顺序；统计快照字段；工程开关默认关闭。每一步带失败断言和要跑的命令。Review Focus 应写下单测覆盖不到、却最可能伤到通话的情况：consent 过期与应用重启的时序、AEC 在重启瞬间的收敛、Wi-Fi 与蜂窝切换。这些条目要么补进某个任务的测试，要么明确留给实验室，不能空着假装检查过。

执行法怎么选，要看任务是否大体独立。若只是应用层状态机加统计，SDD 合适，但信令与媒体共享同一连接对象时，仍不应并行派两个实施者。若还要动 HAL 或厂商音频通道，任务耦合会升高，技能自己也提示不要在不独立时强行 SDD。无论哪种，工作区应在执行阶段建立，并先征求同意；不要在主分支上直接改。

TDD 在这里对「状态机在第 3 次失败后放弃」很有用：先写带伪时钟的失败测试，看见它因功能缺失而失败，再写最小实现，再跑项目套件。它帮不上的是：用 mock 掉的 PeerConnection 去「证明」真机恢复。那种测试往往一开始就通过，或只在验证 mock 被调用了几次——这正是 TDD 技能和 writing-good-tests.md 点名的坏写法。完成门可以要求你出示测试命令输出，但你不能把这份输出说成实验室结论。

收尾时，技能应出示菜单而不是自己合并或推送。若计划或账本里留下了「统计字段在某平台缺失，已延期」这类裁决，必须在最后说明里完整交给人。假设推演到此结束：它展示门能挡住什么，并不证明某款手机已经被修好。

08 / 失败与边界

它会在哪里裂开，以及何时不该用

失败模式机制上为什么会发生不是什么
技能该触发却没触发Windows 未找到可用 bash 时 hook 会静默跳过注入；Unix 仍可回退 zsh，仅在 bash 与 zsh 都不可用时才以退出码 0 跳过。此外，宿主没有 SessionStart；模型忽略描述约束；长会话压缩后丢掉引导。不是「安装了就等于强制执行」。维护者为此写了诊断技能和验收句。
批准前已经写了代码HARD-GATE 只写在技能里。v7 发布说明承认旧版在测试里仍会漏门，并给出他们自己的评测数字；本报告未复现。不是编译失败。对方说「直接做」时，这甚至符合规则。
计划太长或太空技能同时反对「把代码抄进计划」和「TBD」。README 仍提完整代码，可能把模型往旧习惯拉。不是脚本能拦住的格式错误。未闭合代码围栏除外，那个会被 task-brief 拒绝。
做完的任务被再做一遍压缩后只靠记忆。SDD 把这称为观察过的最贵失败，所以要写账本。不是 git 丢提交。提交还在，缺的是控制器承认账本。
评审看上去过了，其实只看了最后一次提交用 HEAD~1 打包。通用评审技能示例仍这样写；执行技能已禁止。不是「评审者无能」，是范围被截断。
单测全绿，产品仍不可用完成门只检查你跑了什么。计划若没有实验室步骤，门不会变出真机证据。不是 TDD 失效，是证据类型被用错。
视觉伴侣或辅助脚本打到错误目录历史问题：相对路径、cd 到技能目录、仓库外写工作区。v7.0.2 针对这些加固，但仍要按正文用绝对路径从工作树调用。不是已经不可能再指错。脚本更硬了，调用方式仍靠模型遵守。

适用

有测试框架、可以用失败测试表达行为、希望代理在改代码前先把目标和代价说清楚的软件工作。对手机应用层的信令、状态机、配置开关、统计和回归测试，尤其合适。也适合需要隔离分支、避免直接在主分支试验的多任务并行开发——前提是先同意建工作区。

不适用或只应部分使用

  • 主要证据在实验室、电台、消声室或真机弱网矩阵里的工作。流程可以要求你把这些写成反目标和未完成项，但不能替你做。
  • 没有测试命令、或只能靠手工听音判断的改动。TDD 铁律在这里会变成空转，或逼出一堆无意义的 mock 测试。
  • 职责紧耦合、无法切成独立可评审任务的大型媒体栈改造。强行 SDD 会在共享对象上打架。
  • 只想改一个确定的图标颜色或一行配置：头脑风暴自己也说，这类事做完并说明即可。
  • 把 Superpowers 当成可以无人看管的发布系统：合并、推送、开 PR 必须等人选，诊断打包也必须先批准。

10 / 边界

和 Matt skills、pstack、OpenSpec 各管一层

三者不是同一类工具，不宜叠成一套互相抢触发的「默认流程」。这里只做边界，OpenSpec 的完整深读由另一篇承担；Matt 的对照以同日已完成的 mattpocock/skills 报告和公开原文为限，不重做审计。pstack 不在本快照内，也不把它的名字写进 Superpowers 清单。本列表对 pstack 的归类与结构，依据同日已审定专题报告（本地稿 research-pstack.html，固定口径 v0.15.42）；本篇未重新审计其源码，也不把 pstack 混同为 Friday Work。

权威工件设计文档和计划默认进 docs/superpowers/；执行账本在 .superpowers/sdd/，默认 gitignore。随各技能而定，例如规格、工单、调研笔记。不要把那些入口算进本仓库的 15 项。变更目录是一等公民；官方 README 强调规格先于代码，并可以跨仓库共享（Stores 为 beta）。playbook、原则、功能技能与使用指南；合入前要求可验证的证据。/setup-pstack 只负责按角色选择模型与推理预算，不是整套工具的全部。已审报告未给出「额度用尽即自动回退」的证据。
怎样开始希望靠 hook 注入和描述自动触发；斜杠命令已删除。更多显式用户入口与路由器，模型可发现的技能并存。官方示例是 /openspec-explore、/openspec-propose、/openspec-apply-change、/openspec-archive-change，也可用自然语言。需要严谨流程时走 /poteto-mode，匹配剧本后再按步骤调用原则和技能。配置层可用 /setup-pstack 选模型与预算。这不是「额度用尽或失败就自动换模型」的入口。
测试观现行 TDD 技能仍把重构放在绿之后的循环里；实施者模板稍松。同日报告指出：Matt 的 tdd 正文把重构移到 review，而 README 仍写 red-green-refactor。两边都要以更具体的正文为准，不能混用口诀。规格里用场景约束行为；它不内建 Superpowers 这套红绿铁律。强调验证，并把「测试绿了」与「可以合入」分开。具体检查清单以已审 pstack 报告为准，本篇不重做。

互补时，比较干净的切法是：OpenSpec 保存「要改变什么、规格怎样写」；Superpowers 约束「这个会话里的代理怎样问、怎样测、怎样审、怎样把不可逆动作交还」；pstack（依据已审定的 v0.15.42 专题报告，本篇未重新审计）提供另一套工程工作流与验证技能，用 /poteto-mode 匹配剧本并调用原则和功能技能。多模型只是它的配置层，不能把它当成额度耗尽自动切换器，也不应与 Friday Work 混同。Matt 的技能若只在 TypeScript 或工单流上使用，应显式调用，避免和 Superpowers 的头脑风暴、写计划同时自动抢入口。factory-gates 这类非官方四门插件，不应当作 Superpowers 本体。

11 / 落地

若要在手机 / WebRTC 工作里用，先定规则再装

  1. 先锁版本。 本报告描述的是 22f0b463 / v7.0.2。按 README 从各宿主市场安装，装到的未必是这一提交。需要可复现时，应自己核对插件 version 与提交，而不是假设 latest 等于本文。
  2. 先写覆盖规则。 在项目 AGENTS 或等价文件里写清：什么时候必须留下实验室验收；什么时候允许跳过提问；禁止在主分支直接改；合并和推送必须等人。这些文字按技能自己的优先级，会压过默认流程。
  3. 计划里把证据类型分开。 能写成失败测试的，走 TDD；只能在真机或实验室看到的，写进 Review Focus 和未完成项，不要让完成门拿单测输出去「证明」通话质量。
  4. 看任务耦合再选 SDD 或 Native。 应用层、接口清楚、任务可独立评审，用 SDD 更稳，也更贵。耦合高或没有子代理，用 Native，并接受终审更弱或后段上下文更差。
  5. 不要同时开三套规划体系做默认触发。 若已用 OpenSpec 管变更目录，就让 Superpowers 从已批准的规格进入 writing-plans，而不是再头脑风暴出第二套互相矛盾的设计。
  6. 安装与商业支持只作摘录。 README 列了 Claude Code、Cursor、Codex、Gemini、Devin 等许多宿主命令，也提供 sales@primeradiant.com。本文未执行其中任何命令，也不评估各宿主的实际注入是否成功。
