先把代码库、lint、类型做成硬约束，再把验证做强，最后才自动化外循环。顺序反了，自动化只会更快地产出垃圾代码。

题目：All Code Is Slop (Except Mine)，直译“所有代码都是垃圾（除了我的）”。官方页标注 2026 年 11 月 11 日主舞台；当天直播里是 1:01:02–1:18:38。单独剪辑的视频在北京时间 11 月 15 日 02:30 上线 YouTube，时长 17 分 31 秒，封面标语是 “Review Proof, Not Code”（审证据，不审代码）。

讲者：Lauren Tan，网名 poteto（转写识别成 “Potato”）。官方页写她是 SpaceXSI 的 Principal Engineer；她在演讲里说自己做 Grok Bot（转写里的 Grabbot、Grockbot、graphbot 都指 Grok Bot，YouTube 简介写的是 “the Grok Bot team at SpaceXSI”）。pstack README 里她自述在 Meta、Netflix、Cursor 工作过，也在 React 核心团队参与 React Compiler。

出发点：以前只有极少数“coding machine”才有超高产量，现在有了 agent 人人都能做到。她的论点是，工程师的新“元工作”是在产量暴涨的同时保持甚至提升代码质量。别人叫它“软件工厂”，她更愿意叫它“信任”。她说自己花了大约 6 个月，才走到能合入上千个 PR、很多还是在睡觉时合入的程度。

“I like to keep it simple and I think of it as all about trust. Not blind trust, but investing in your agents environment so you can trust that your agents are going to do the right thing.” ▶ 1:31

我更愿意说得简单点：关键是信任。不是盲目信任，而是投资 agent 所处的环境，让你能相信它会做对。

信任金字塔：时间先花在哪一层核心框架▶ 2:03倒金字塔，越上面越优先投入：代码库 → 静态分析 → 验证 → 文字规则 → 人工审查。

幻灯片标题 “how do i trust my agents more?”，副标题 “the poteto pyramid”。她口头讲了前四层：

前两层是确定性的：代码本身（好的 API 设计、架构、重构），以及 lint、类型系统、编译器、各种测试。两层一起用，能约束 agent，让它“默认就做对”。

第三层验证：运行时和形式化验证，用来找 bug、检查系统里应该一直成立的性质，也用来确认 agent 理解了你的目标和意图。

第四层文字：rules、skills、AGENTS.md，留给需要判断的事。幻灯片上还有第五层 “human review”（人工审查），左边有一根指向下方、标着 “cost” 的箭头。

推断这根箭头的意思应该是越往下成本越高，靠文字和人工兜底最贵、最不可靠，所以要尽量在上层解决问题。她口头没有解释这根箭头。

“whenever you're correcting your agent, think about how you can make that a deterministic check instead of adding another line to your rules or your agents.mmd because it's far more reproducible when it's in code and it lets you trust it more.” ▶ 3:15

每次纠正 agent 时，想想怎么把它变成一条确定性检查，而不是往规则文件或 AGENTS.md（转写误作 agents.mmd）里再加一行。写在代码里可复现得多，你也更敢信它。

从“人兜底”到“工厂”：三个循环▶ 1:48▶ 16:02低信任：agent 写垃圾、人来验证；高信任：agent 写好代码、自己验证；工厂：在高信任循环上加自动触发。

演讲开头和结尾各出现一次这组图。开头只有前两个圈：“low trust（多数人卡在这）”→“high trust（你想去的地方）”。结尾加上第三个圈 “factory”，标注 “trust enables scale”（信任撑起规模），底部写着 “improve your loop before automating!”。

她的意思很直接：工厂不是起点，是做完金字塔之后自然得到的东西。

代码库就是花园：agent 会照抄你留下的一切▶ 3:35代码是 agent 最大的输入。workaround、反模式、废弃写法都会被下一个 agent 当成“既定写法”照抄。

她 2024 年上班要审同事写的 3 个 PR，现在这个数字更像 300。每个工程师背后都是成百上千个 agent，代码像连续的水流一样涌进来，“几乎像一个活的东西”。

在这个比喻里，你设的约束和护栏是混凝土地基，新代码围着它们生长。反过来，代码里留着的 workaround 和技术债会被下一个 agent 当样板照抄，像杂草和害虫一样蔓延。所以要让代码库尽量干净，agent 抄到的永远是好东西。

“code is the biggest input for agents. It means that any workarounds um anti-atterns deprecated code tech is now likely to be just copied by the next agent since it looks like the established pattern in your codebase” ▶ 4:26

代码是 agent 最大的输入。这意味着任何 workaround、反模式（转写误作 anti-atterns）、废弃代码、技术债，现在都很可能被下一个 agent 照抄，因为它看起来就是你代码库里的既定写法。

Dune 框架：让错误写法根本写不出来▶ 5:00禁用 useEffect、用目录结构表达主进程和渲染进程的边界，从此这两类问题不用在代码审查里查。

Dune 是团队给 Grok Bot 做的客户端框架。她说它技术上不复杂，“可以理解成 Electron 应用版的 Next.js”；有意思的是里面编码了做桌面应用学到的大量约束和 lint 规则。幻灯片把它拆成：应用框架（导航、渲染、IPC）+ 一个功能一个文件夹 + 严格的 import 禁令 + 代码里不写注释。

例一：禁用 useEffect。她的经验是，需要细腻判断才能用好的东西往往会产出 slop。React 的 useEffect 有正经用途，但经常被误用，agent 也用不好，所以产品代码里直接禁止，只在 Dune 的 API 内部少数地方允许。“这个问题被整类消灭了，代码审查里再也不用抓它。”

例二：用目录结构传递上下文。在 Cursor（同样是 Electron 应用）里，agent 经常把主线程代码 import 进渲染线程，造成长任务和卡顿。在 Grok Bot 和 Dune 里，两个顶层目录就叫 electron-renderer 和 electron-main，两者之间的 import 被依赖图分析器和 lint 规则禁止。

“these are simple lint rules to set up but it means one less thing that we need to review and think about” ▶ 6:49

这些 lint 规则设置起来很简单，但意味着代码审查时少看、少想一件事。

注释是负债：它给 workaround 发“许可证”▶ 6:56agent 用注释解释“为什么这个补丁合理”，下一个 agent 就照着做。Grok Bot 禁掉了约 99% 的注释，换成能报错的 lint。

她举了 Cursor 的例子：agent 特别爱用 setTimeout、requestAnimationFrame、requestIdleCallback 这类命令式定时器当快速补丁，根子其实是 VS Code 的命令式风格和 React 的声明式风格之间的架构冲突。大量定时器被频繁创建销毁，会引发大量 major GC，造成卡顿。

更糟的是 agent 写了很多注释解释“这个补丁为什么合理”，没多久定时器就到处都是，应用性能明显变差。

所以 Grok Bot 决定禁掉约 99% 的注释：容易过时，人也懒得读，还给 agent 一个“这事太难所以不做对”的逃生口。取而代之的是带清晰报错信息的 lint 规则，告诉 agent 去修根因，而不是绕过去。

“the worst part about comments though is that they're not enforcable. So what seems well-intentioned, you know, like I'm going to tell the the next agent not to do something, never ends up actually being anything that you can trust.” ▶ 8:45

注释最糟的地方是没法强制执行。看起来用心良苦，比如“我要告诉下一个 agent 别这样做”，但它永远不会变成你能信任的东西。

总原则：每一次纠正，都变成一条确定性检查最重要的一条▶ 9:14做得足够多，审查时就“没什么可看的了”，agent 可以自己合并大部分 PR。

“our general principle is that every time we correct our agents, it turns into one of these deterministic checks or we think about how to categorically eliminate that problem in the code through better API design, through better uh architecture.” ▶ 9:14

我们的总原则是：每纠正 agent 一次，就变成一条这样的确定性检查，或者想办法通过更好的 API 设计、更好的架构，在代码里把这个问题整类消灭。

“at some point, you'll realize there's there's nothing left to review, and you can just let agents merge their most of their own pull requests.” ▶ 9:35

到某个时候你会发现已经没什么可审的了，可以让 agent 自己合并大部分 PR。

推断这张图的阶梯曲线横轴是 7 月到 11 月的日期，数值从 2 涨到 167；她没有口头说明纵轴单位，看起来像累计的检查或 lint 规则条数。

pstack 里专门做这件事的技能是 /correct，见第六节。

验证：代码审查变成看“证据”▶ 9:40▶ 10:50▶ 11:51审查改成看视频、截图、图表和形式化验证结果。运行时验证、TLA+、Lean、Bombadil、状态图一层层叠上去。

运行时验证：给 agent 一个自己跑代码的办法，用人类开发者也用的调试工具，比如 Chrome DevTools Protocol。验证技能里有一份功能地图（feature map），像网站地图一样从用户视角列出所有功能，你说“左边栏那个东西”时 agent 不用猜。技能里还用自定义 CLI，agent 每次复用同一个 CLI 和驱动，既省 token 又可测试。

形式化验证：用 TLA+ 对主要用户流程做模型检查，比如跨设备、跨平台的通知；用 Lean 证明某些算法，比如团队自研的虚拟列表库不会闪烁或抖动。已经找到不少 bug，但她说“不是银弹”，只是又一层。

UI 属性测试：刚开始用 Bombadil，也抓到了几个 UI bug。

状态图：她在 pstack 里做了 statechart 技能，从用户视角把状态机画出来，她觉得和视频、截图一起看更容易审。

token 花在哪：她引用 Cindy 的推文：半年前因为细微 bug 不敢信 agent，现在每天 70% 的 token 花在验证上。她说这和自己的情况一致。这些技术都不新，只是过去写和维护太贵，agent 把成本打下来了。

“we're entering a golden age of software testing and verification because agents let us test everything to a much greater degree than used to be economical.” ▶ 12:46

我们正在进入软件测试和验证的黄金时代，因为 agent 让我们能以过去不划算的深度去测试一切。

收尾：外循环最后再搭▶ 15:11内循环产出 slop，自动化它只会产出更多 slop。地基好了，发版后自动 fuzz、开修复 PR、自动合并才变得可行。

她给的顺序：纠正 agent 时先改代码库，先上一条 lint 阻止新增反模式，再清理旧写法，然后把验证做扎实。这些工作反正是自动化的前提。

地基好了，外循环就容易搭。她推荐用 Grok Bot：很多连接器，能拉起 Cursor 云端 agent 的 routines，以及能编排成百上千个 agent 的 projects。

例子：每次发新版，Grok Bot 自动开一个 Cursor 项目，对整个构建做 fuzz，像真实用户一样用应用找 bug，为每个 bug 开修复 PR 并自动合并。她说能这么做，是因为代码库好到 PR 默认就是好的，大多数产品代码已经不需要深度人工审查。

“if your inner coding loop uh produces slop, then automating that loop just produces more slop and you need to throw more and more and more tokens at the problem” ▶ 15:40

如果你的内循环产出 slop，自动化这个循环只会产出更多 slop，你得往问题上砸越来越多的 token。

三、pstack 总览与结构3 节
pstack 是什么：“想快，先深”v0.15.42MITpoteto 的个人工程栈，发布在 Cursor 官方插件仓库 cursor/plugins 里，MIT 协议。

README 开头她说：AI 写了太多垃圾代码，这点她同意；她不想像“二十个 slop 艺术家组成的团队”那样交付，没有质量的吞吐量不是她的目标。原话 “if you want to go fast, go deep first”（想快，先深）。目标不是最大化代码行数，恰恰相反，是写更少但质量更高的代码。

第二个卖点是“无畏的并行”（fearless parallelism）：当你能深度信任一个 agent 写出可验证的好代码，才能真正放心地开多个 agent 并行。

第三个是多模型：README 说很多技能用多模型工作流，利用各家模型的长处。默认分工：写代码的剧本（功能、重构、修 bug、性能、爬坡）、文字和判断给 Opus 5.5，最难的改动给 Fable 5.2，评审面板默认 Fable 5.2 / Opus 5.5 / Gemini 4 Carbon。这是 v0.15.42（线上最新提交，北京时间 11 月 15 日 11:36）刚换的默认值，Grok 4.7 不再是默认；/setup-pstack 可以改。

六、四个与演讲对得最紧的技能4 个

每个都读过线上 v0.15.42 的 SKILL.md 原文，写清做什么、怎么用、为什么。

/correct：把“纠正 → 检查”变成一个技能对应 6:56–9:40找出 agent 在这个仓库里反复犯的错，按“架构 → 类型/lint → 测试 → 文档”的顺序让它不可能再犯。
做什么

读最近的提交、回滚、评审意见、agent 规则文件，以及解释 workaround 的注释，把错误归类（出现两次才算一类）。然后在能起作用的最高一层修掉每一类。

怎么用

直接输入 /correct，它不会被模型自动调用。技能描述里写着：每次你纠正 agent 后都重复一次。

为什么

对应演讲最核心的一句：纠正要落在代码里，不是 AGENTS.md 里。技能的前提假设很说明问题：每个贡献者都是“只看自己打开的文件、照抄最近的例子、走能编译的最短路”的 agent。

① 用架构消灭每块状态一个主人、每件事一种正路；隐藏内部，让错误的 import 直接失败；手工同步的列表换成单一来源；删掉 agent 会照抄的旧写法和死代码
② 用类型强制坏状态写不出来；还能编译的话，加 lint 或 CI 检查，报错里直接写该改用哪个文件、类型或函数；已经很普遍的写法，只在“新增”时报错
③ 测试行为修掉或删掉“行为坏了还通过”或“只改内部就失败”的测试
④ 最后才写文档只留给判断类问题，因为 agent 跳过它时什么都不会失败

两条很硬的要求：每条新检查都要证明它能在一个真实的历史错误上失败；本地和 CI 跑同一条命令。例外写在出问题的那一行，带理由、过期日期和人工批准。

规则对照表：在 agent 规则文件里维护一张“规则 ↔ 由什么强制执行”的表。如果某条规则早就写着却没有东西强制，那就算“重犯”，在同一个改动里升到最高层去修；错误不可能再发生时，就删掉这条规则。

回复格式：每一类错误 + 证据 + 选了哪一层 + 为什么更高层不行

/statechart：把状态机画给“懂产品的人”看对应 10:50写 TLA+ 模型，用 TLC 检查，再画成用户视角的 Mermaid 状态图，标出哪个状态违反了哪条规则。
做什么

检查一个会在多个状态之间切换的系统（产品流程、协议、服务）的 TLA+ 模型，画成 Mermaid 状态图。报告给出到达每个违规状态的最短路径。

怎么用

在仓库外的临时目录写 TLA+ 规格和配置，运行 scripts/statechart SPEC.tla [--config] [--view] [--out]（TypeScript 脚本）。第一次运行会用 mise 安装 TLC 和 Java，需要联网。

为什么

演讲里她说状态图和视频截图一起审更容易。她在 X 上的解释：只有你知道产品应该怎么工作，所以要让你能用眼睛确认它是对的。

写 TLA+ 规格→读者同意的每条规则写成 INVARIANT→TLC 模型检查→view 模块翻译成读者的话→Mermaid 状态图 + 违规最短路径

几条讲究：绝不为了让规则成立而弱化规则；状态和箭头标签用读者看得到、关心的话，比如“you press play [while the file loads]”，不出现变量名或代码名；一张图目标约 20 个箭头以内，太乱就合并标签，但不能合并违反不同规则的状态；模型超过 500 个状态时只画通向违规的路径。

交付时：每个 bug 一行（规则、读者能懂的规则描述、编号路径）；如果模型描述的是真实代码，要把每条 bug 路径在真实代码上复现一遍，复现不出来时先假定模型错了。

/no-comments + Comment Sicko：一个“恨注释”的审查员对应 6:56派出只读子 agent 删注释、标出该重构的代码，再把注释里声称的约束换成类型、测试或 lint。
做什么

对当前 diff（默认对比 main）派出 Comment Sicko。它只删注释、把该重构的符号标成 MUST KILL，不碰应用代码。主 agent 审它的报告，修掉被接受的问题，并为“do not remove”这类约束注释提供可执行的替代。

怎么用

输入 /no-comments；poteto-mode 规定“审查前”必跑。

为什么

对应演讲“禁掉 99% 的注释”：注释会过时、没人读、给 workaround 找借口，而且没法强制执行。幻灯片上写着 also see /no-comments in pstack。

Comment Sicko 放过的
  • 法律或许可证头
  • 外部依赖、平台、厂商、协议强加的、我们改不了的反直觉行为
  • // prettier-ignore
  • 定义公开 API 契约的文档注释
  • 解释代码表达不了的约束的 issue 或 RFC 链接
它要删的
  • 旁白、横幅、注释掉的死代码
  • 为 workaround 辩护的长篇说明（原文：长篇辩解就是认罪）
  • 我们自己代码里的“意外”：删掉注释，并把对应符号标 MUST KILL，要求改名、抽取、加类型或重构
  • 保护正确性或安全的规则上的 eslint-disable、@ts-ignore
  • 拿不准是否属于例外的，一律删
1派出 Comment Sicko传入范围，不复述它的规则
2审它的报告驳回越界改应用代码、删了受保护例外等问题；遇到 “IMPORTANT / do not remove” 先追溯符号或跑 /why
3修小问题直接删死路径、去掉参数、改用真正的 API；需要改形状就跑一次 /architect，只出草图
4修根因在范围内做最小的根因修复，删掉所有点名的 workaround，不加症状级防御
5约束注释 → 编码提供最便宜的类型、运行时检查、测试或 CI lint，经批准后先编码再删注释
6报告删除数、恢复的注释、重跑次数、修复、仍未强制的约束

八、夜间运行：pstack 的“外循环”3 节
夜间循环：一次改动、一次检查、一行日志指南第 7 章检查完成条件 → 最小改动 → 对真实产物验证 → 有进展就提交、没进展就丢弃 → 记一行决策 → 回到开头。

指南第 7 章：每轮只做一次改动、一次检查、记一行日志。没帮上忙的改动直接丢弃，不留着搭车。遇到平台期要换思路而不是停下，完成条件绝不悄悄放宽来宣布胜利。

放手之前的四个条件和一份“夜间合同”先赢得信任再开循环：你亲手做过、agent 有你的工具、每一步能叫停、重复失败已经变成检查。
1你知道“好”长什么样亲手做过一次，或者看着 agent 做过一次
2agent 有你会用的工具验证技能、profiler、日志
3每个阶段都证明自己不达标时能叫停整条线
4读过几份转写并把重复出现的失败变成工具、技能或检查

四条都满足才让它自己跑，否则在旁边看着跑。

九、可以直接借鉴的做法（写给手机厂商程序员）7 条

第 1、2、5、7 条来自演讲，第 3、4、6 条来自 pstack 源码和指南。标“推断”的是本报告按手机端场景做的类比或建议。

1 · 同一个错第二次出现，就写成检查

别加进提示词或规则文件。Android 可以写 Android Lint 自定义规则或 detekt 规则，iOS 可以用 SwiftLint 自定义规则，C/C++ 可以用 clang-tidy；报错信息里直接写“改用哪个类或函数”。推断具体工具是按手机端常见技术栈给的建议，演讲没有提到。

2 · 用目录和模块边界表达架构

演讲里的 electron-main / electron-renderer 很像手机端的 UI 层、系统服务层、native 层。把边界做成模块依赖规则，让错误的 import 编译不过。推断对应关系是类比。

3 · 给 agent 一套能自己跑起来验证的环境

照 /create-verification-skill 的五节来写：模拟器或真机的启动、体检、驱动（adb、UI Automator、XCUITest 等脚本化入口）、取证（截图、录屏、日志）、清理，再加一份从用户视角写的功能地图。推断具体驱动工具是建议。

4 · 有状态的流程，先画状态图再写代码

相机、通话、蓝牙连接、OTA 升级、权限申请这类多状态流程，适合用 TLA+ 建模 + /statechart 出图，让懂产品的人用眼睛核对。推断场景是按手机业务举的例子。

5 · 少写解释 workaround 的注释

注释里写“这里先这样，因为……”，等于教下一个 agent 照抄。改成修根因，或者用 lint 把这种写法拦住。

6 · 先单独试几个技能

/correct、/unslop、/why、/no-comments 可以直接点名使用，Claude Code 里也能装 pstack。全套 /poteto-mode 会多花 token（指南原话：严谨的代价），先在一个小仓库试。

7 · 注意边界

她的数字是自家团队自报，不是对照实验；她也说花了约 6 个月打地基。外循环（自动 fuzz、自动合并）放在最后。
