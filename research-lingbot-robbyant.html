01　灵波是谁，LingBot 指什么

先把公司和产品线分开：灵波是公司，LingBot 是公开模型家族，R2 等是硬件与配套软件。

官网英文页的主句是 “Building One Brain for All Robots”，并自称提供从空间感知、动作模型到环境奖励的全栈具身智能。页脚署名 Robbyant（Shanghai Ant Robby Technology Co., Ltd.），销售与合作邮箱使用 antgroup.com 域名，技术站与 BusinessWire 通稿都把它写成 Ant Group 旗下的 embodied AI 公司。[S05][S04][S27]

同一套官网还区分产品层与模型层。文档中心除了 LingBot 模型手册，还有通用人形机器人 R2 的产品手册、RobbyantGo、RobbyantTeleop、RFrame 与 RobbyantStudio；R2 文档里的 /navi/* 接口是机身导航通信，不是 LingBot-Navi 模型。两者不要并成一条产品线。[S01]

LingBot 这个名字覆盖一组各自独立的仓库和检查点。中文文档首页把「五个开源模型」写成：根据相机与语言生成动作的 LingBot-VLA，在同一自回归序列里建模视觉动态与动作的 LingBot-VA，生成可控长时环境的 LingBot-World，优化残缺深度的 LingBot-Depth，以及从连续图像重建三维场景的 LingBot-Map。文档明确要求：不要把所有模型装进同一个环境，因为各仓库指定的 Python、PyTorch 和 CUDA 版本并不相同。[S01]

技术站首页的目录比文档站更全，还列出了 LingBot-Vision、LingBot-Touch、LingBot-Video 和 LingBot-Navi，并为 Map、VLA、VA、World 标明了 1.0 / 2.0 入口。这是「家族已经公开哪些名字」，不是「文档站已经写完哪些安装说明」。[S04]

03　「通用大脑」在文档里怎样被拆开

把口号落到可以点开的页面和仓库，而不是把它当成已经跑通的端到端系统。

通稿把 Map 2.0 与 Navi 写成“加强灵波通用具身大脑，从空间感知到高效导航”。技术站则用 “one brain for all robots” 和 “full-stack embodied intelligence” 来总括整组模型。这些是官方口径，本文只用来定位宣传位置，不把“通用”当作评测结论。[S27][S04]

能核对的拆分是分层的。文档站把开源模型按任务列成一张表：VLA 输出动作序列，VA 输出视频-动作预测，World 生成视频，Depth 输出优化深度与三维点，Map 输出相机轨迹与三维重建。技术站在此之外补上 Vision（面向稠密空间感知的视觉基座）、Touch（跨传感器触觉表征）、Video（多场景视频生成）和 Navi（带空间记忆的导航）。[S01][S04]

模块之间的接口在文档里是“被提到”，不是“已经提供一份联合运行手册”。Map 2.0 技术报告写明，多视角离线训练的图像编码器从 LingBot-Vision-L 初始化，并在消融里把它和 DINOv3-L 对比。Navi 技术报告写明，记忆可以由仿真器深度与位姿构建，也可以改用 LingBot-Map 重建的几何；导航权重在 Map 1.0 重建上训练，评测时可以把建图引擎换成 Map 2.0。这些是报告中的训练与评测设定，不等于仓库里已经有一条“Vision → Map 2.0 → Navi → VLA”的一键脚本。[S14][S19]

文档站与技术站不同步。截至本次抓取，docs.robbyant.com 的 sitemap 仍只有 LingBot-Depth / Map / VA / VLA / World 的模型手册，论文页也只链到这五个模型的 arXiv；Map 2.0、Navi、Vision、Touch、Video、World v2、VLA v2 要以技术站、GitHub 和模型卡为准。[S03][S02]

04　Map 2.0 的流式重建与再巩固

报告要解决的问题很具体：流式重建把误差留在内部上下文里，事后只改输出轨迹，帮不了后面的帧。

技术报告开篇把 LingBot-Map 2.0 写成对 LingBot-Map 的增强：流行的流式系统对每帧往往只走一遍，误差会随时间累积。2.0 采用分层策略——下层继承 1.0 的流式能力，上层可以在流式模式和再巩固模式之间切换。两种模式共用同一组权重，差别只在使用因果注意还是双向注意。再巩固可以在任意时间步触发，上层对已选关键帧联合重算，并把精炼结果写回 KV 缓存，使后续流式步骤读到更新后的上下文。这一能力被命名为 Geometric Context Reconsolidation（GCR）。[S14][S06]

方法部分把这件事说得更形式化。模型在线处理有序 RGB 流，为每个视图预测相机与深度，并在流推进时修订更早的预测。关键句是：修订的对象是“产生这些估计的几何上下文”，而不是只修正输出本身。更新内部上下文会同时改正历史几何，并刷新未来视图所读取的状态。[S14]

它建立在 LingBot-Map 的 Geometric Context Transformer 之上：每个视图被标记为图像 token，并配上相机 token 与 register token，经过 L = 24 层、层内帧注意与跨视图 Geometric Context Attention（GCA）交替，再由因果相机头和多层 DPT 头解码相机与深度。GCA 保持跨视图注意的因果性和紧凑性，上下文来自三类来源：固定初始化前缀 A 建立共享坐标系与尺度，局部窗口 Wt 用最近关键帧配准当前帧，更早关键帧只贡献上下文 token 作为长程轨迹记忆。[S14]

再巩固时，已提交层的缓存保持不变，只重开可修订层，用存储的 token 做一次前馈重算；共享的相机头与深度头据此更新历史估计，后续帧直接读重写后的上下文。项目页把它概括为：不必做回环检测，也不必做位姿图优化或后处理。这是设计主张，评测比较见下一章。[S06][S14]

训练分两段：先得到因果流式基座，再做混合模式连续训练

第 4.1 节先做多视角离线训练：图像编码器从 LingBot-Vision-L 初始化，输入长边缩放到 512 像素，按 16×16 斑块进入 24 层主干；这一阶段使用密集的跨视图注意、不打因果掩码。然后把全部 24 个跨视图层切到因果可见性，序列长度从短片段逐步扩到长轨迹，局部窗口 W 在 [16, 64] 中采样。这一课程学习得到的是「加强后的几何流式基座」，用于纯因果在线重建。[S14]

第 4.2 节说明，如果直接把纯因果权重的上层改成双向再巩固，位姿精度会严重下降。因此需要混合可见性采样，让可修订层在同一组权重下见到因果、双向和“已再巩固前缀”等注意模式。Table 5 在更轻的训练日程上给出累积消融：把混合模式加进去之后，KITTI 上 GCR 的 ATE 从约 63 m 降到 14.96 m；若不对因果基线做混合训练就直接再巩固，ATE 会从 24.04 m 升到 72.28 m。[S14]

Table 7 比较 24 层的切分。只留 8 层可修订时，GCR 的 ATE 是 17.40 m；12/12 切分是 14.96 m；24 层全部重开是 16.06 m，还要付出双倍再巩固计算，并失去已提交缓存的不变性。主模型采用 12+12。这些数字来自较轻日程的消融，不是主表里的最终检查点。[S14]

推理速度数字写在哪，以及它量的是什么

报告在 KITTI 07 的 1,101 帧上，单卡、预热之后测量吞吐，不含模型加载和磁盘 I/O，但包含适用的回环阶段。Ours (Online) 为 27.51 视图/秒，该设定下 11 条 KITTI 的 AUC@30 为 77.28。在已有因果缓存、不计入缓存构建的前提下，只对 373 个保留关键帧做再巩固是 21.41 缓存关键帧/秒，AUC@30 升到 87.73。把全流在线推理和序列末再巩固合在一起，端到端吞吐是 19.17 帧/秒。通稿也提到单卡 RTX 5090 上 27.51 FPS；报告正文这段没有在摘录中写明 GPU 型号，通稿中的设备名应视为通稿自己的表述。[S14][S27]

05　已经发布的是哪一个检查点

文件名里有 GCR，不等于混合模式权重已经公开。

仓库 README 写得很直接：本仓库提供技术报告中的几何流式基座模型（不含 GCR），为因果 Online Streaming 训练。Hugging Face 模型卡重复了这一点：这是纯因果流式基座，不是混合模式 Geometric Context Reconsolidation 检查点。格式为 PyTorch 张量状态字典，1,365 个张量，不含优化器或训练状态；配套 config.json 与 model_weights.pt；SHA-256 为 d3ae62a09d3caaeb0947c4372f6fb23a4c0e85304867fa9702948ba030310e27，与仓库里的 configs/base-streaming.json 一致。[S11][S21][S15]

已发布配置还写明：training_mode 为 causal，architecture 为 dinov3_vitl16_causal24，空间 RoPE 为 max，scale_frames 8，sliding_window 64，camera_iterations 4，max_frames 1024，输入 512×288。加载器会核对 SHA-256、因果训练模式，以及每个参数键和形状。[S15][S21]

这里有一处必须并列写清、不能自行抹平的差别。技术报告第 4.1 节说主训练的图像编码器从 LingBot-Vision-L 初始化；公开配置字符串却是 dinov3_vitl16_causal24，仓库里的编码器实现也改编自 DINOv3，并同时带有 DINOv3 License 与 FAIR Noncommercial Research License v1。本文未加载权重，不能断言已发布检查点的初始化来源，只能同时记录这三份一手文本。[S14][S15][S13]

源码方面，lingbot_map2/models/gcr_base.py 和 gcr_stream.py 的文件名容易让人以为 GCR 推理已经放出来。读加载函数后，结论相反：模块文档字符串是 “Public API for the pure causal LingBot-Map2 streaming release”；load_model 在检查点元数据不是 causal 时会报错；写入的 metadata 是 “LingBot-Map2 Streaming (causal-only)”。仓库里没有单独的再巩固推理入口，评测脚本也是对着这份因果发布配置写的。[S16]

关于能否不登录就下载：README 仍写 “The model repositories are currently private”。本次拉取时，Hugging Face API 显示 robbyant/lingbot-map-v2-base-streaming 为 private: false、gated: false，模型卡和 config.json 可匿名读取。旧的路径 robbyant/lingbot-map-v2 会 401，真实模型 ID 是带 -base-streaming 的那一个；ModelScope 镜像仍叫 Robbyant/lingbot-map-v2，许可字段为 cc-by-nc-4.0。本文没有下载 model_weights.pt（约 4.6 GB 存储占用）。[S21][S20][S25]

07　Navi 的空间记忆与指令导航

Navi 要处理的是：机器人多次进入同一环境时，怎样用已经见过的表面回答新的指令，而不是每次从零探索。

技术报告把空间记忆写成带特征的点云：每个采样到的表面位置，配上预训练视觉语言模型的特征，成为三维视觉 token。系统有两种工作制度：还没有记忆时，按占用栅格做自主初始探索；记忆就位后，由 Scene-aware Navigation Transformer 做检索、定位和路线规划。若检索没有匹配，就做目标导向的前沿探索，并在新观测到来时在线更新记忆。报告还写了初步的歧义消解：在多个匹配物体之间描述差别，供使用者选择。局部规划器执行预测路线，并给出在边缘设备上运行的时间测量。[S19]

数据集与基准是随模型一起公开的。报告与数据集卡一致写到：共 511 个真实采集场景，训练 475、测试 36，覆盖 7 类场所、103,522.67 平方米可通行面积。领域计数包括机构 129、商业 142、公共空间 86、办公 67、工业 58、休闲 28，另有 1 个标为 Other。平均可通行面积 202.59 m²，中位 167.02 m²，最大 1,242.99 m²。完整数据集在 Hugging Face 上标记为 gated: manual，许可为 CC BY-NC-SA 4.0；测试归档可从 LingBot-Navi-Test 下载，不必申请访问。[S19][S23][S24]

08　Navi 与 Map，以及同栈其他模型如何相接

接口写在报告的评测设定里，不写成已经开源的联合运行栈。

Navi 论文把几何来源分成两类。一类使用仿真器深度与位姿，把观测放到同一坐标系。另一类使用 LingBot-Map：图像提供局部几何，仿真器里程计提供尺度，再用一个相机位姿锚定记忆。硬件上，报告只作为可能路径提到 RGB-D 或标定双目提供度量深度、机载里程计用于建图，并引用 ORB-SLAM3；这不是已发布的真机部署记录。[S19]

致谢与依赖也说明了边界。Navi 仓库写明：语言与视觉骨干来自 Qwen3.5-4B；位姿头改编自 Pi3；流式几何重建来自 LingBot-Map（链接指向 1.0 仓库）；渲染参考 gsplat 与 Brush。Map 2.0 仓库则建立在 LingBot-Map、LingBot-Vision、VGGT、DINOv3 和 FlashInfer 之上。两边都没有把 VLA 或 World 接进同一条推理图。[S17][S11]

同栈其他模型各自独立发布，和这次 Map 2.0 / Navi 切口的关系是「家族并列」，不是一条已经开源的控制闭环：

  • LingBot-Vision：边界中心的自监督视觉基座，技术站与仓库在 2026 年 7 月公开；Map 2.0 报告把它写进训练初始化，但已发布 Map 2.0 配置并未写明 Vision 权重路径。
  • LingBot-Depth：掩码深度建模，是文档五模型之一；技术站另有 Depth 2.0 的叙述，需以对应页面和仓库为准，本文未把 Depth 2.0 当作已核完的发布包。
  • LingBot-VLA / VLA v2：文档与技术站给出 VLA 的动作生成角色；VLA v2 模型卡提到约 60,000 小时预训练等数字，不在本次 Map/Navi 核验范围内，只作为家族条目列出。
  • LingBot-World / World v2、VA、Video、Touch：技术站均有专页和仓库，许可与检查点见下一章清单。它们不参与 Navi 报告的导航表格。

文档还提醒：各官方仓库指定的运行环境并不相同，不能假定装在同一环境里就能串联。[S01]

Map 2.0 是这次最容易误读的一处。它不像多数 LingBot 仓库那样把代码放在 Apache-2.0 下，而是把原始代码和基座权重一并放在 CC BY-NC 4.0。第三方声明写清：这一默认许可并不取代 DINOv3、VGGT / VGGT-Omega 改编文件的上游许可；可视化与部分层文件仍按 Apache-2.0 保留原版权声明。[S12][S13][S21]

World v2 是家族里另一处明显收窄：仓库根 LICENSE.txt 与模型卡均为 CC BY-NC-SA 4.0，和 World 1.0 的 Apache-2.0 不同。[S04]

未随这次发布放出的，至少包括：Map 2.0 的混合模式 GCR 检查点与完整再巩固推理入口；Map 2.0 技术报告的 arXiv 版本（README 仍写 Coming soon）；文档站上的 Map 2.0 / Navi 安装手册；以及将 Vision、Map、Navi、VLA 串成单一“通用大脑”运行时的官方一体化代码。内部训练数据除 Navi 已公布的 511 场景和各模型卡已列数据集外，其余未在本次材料中逐项核实。

10　能核到哪一层，就只下那一层结论

下面这些判断停在已经打开的文本和元数据，不再往前走一步。

  • 可以确定：灵波公开了一个多仓库的 LingBot 家族；Map 2.0 与 Navi 的公开 GitHub 仓库出现在 2026 年 11 月 26 日（北京时间），不是 27 日才首次发布。
  • 可以确定：Map 2.0 技术报告提出了可在模型内部写回的 GCR 机制，并在混合模式最终检查点上给出长轨迹、稠密重建和回访表格。
  • 可以确定：当前 GitHub 与 Hugging Face 放出的 Map 2.0 权重是纯因果流式基座，模型卡和加载代码都排除了混合模式 GCR 检查点。因此不能声称“开源包已经覆盖报告中的 GCR 数字”。
  • 可以确定：Navi 的代码与权重按 Apache-2.0 发布，数据集按 CC BY-NC-SA 4.0 发布且完整训练数据需申请；Table 3 的导航数字应按“谁来执行路线、用什么几何”分组阅读。
  • 不能确定：已发布因果基座在同一套协议下会得到什么样的 Online 误差；本文没有跑推理，报告也没有为这份因果检查点单列主表。
  • 不能确定：README 中 11 月 21 日、23 日的内部时间线是否对应过任何公开页面；GitHub 仓库在 26 日才存在。
  • 不能把“通用大脑”理解成已经开源、已经在真机上验证的单一系统。真机部署、作者在 Thor / 5090 上的时延，以及仿真器里的导航成功率，都还停在报告自己的实验描述里。
