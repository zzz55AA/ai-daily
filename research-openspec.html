01

一、快速结论：给 AI 一套可回读的工程契约，而不是更长的开场白

对手机 OEM / WebRTC 工程师，OpenSpec 最值得研究的不是“先写文档再编码”，而是把一次变更拆成有名字、有路径、有依赖、能重新读取的工程对象。 对话中说过的需求，变成能审查的规格；准备改什么，变成独立的 delta；实现推进到哪里，回到文件与任务清单查询。它降低的是“意图散落在聊天里”的风险，不会自动解决竞态、音频时序或设备兼容问题。

官方身份已交叉核对：官网 openspec.dev 链向 Fission-AI/OpenSpec，仓库 README 回链官网文档，包声明为 @fission-ai/openspec。本篇固定在 2.1.1 / 0c737dc1b543249b38b0f4716816fcf493d894dd，提交时间为 2026-11-20 06:15:20 北京时间；核验日期为 2026-11-21 北京时间。这是研究快照，不是对未来版本的保证。官方站 ↗ README.md L157–166 ↗ package.json L1–18 ↗

先记住四个判断。**第一，OpenSpec 是规格与变更工作流，不是运行时框架。第二，产物存在不等于内容正确，任务打勾不等于真机验证通过。第三，智能同步技能与 CLI 归档不是同一条执行路径。第四，当前 2.x 交付 skills，旧文档里的 /opsx:* 不能原样当作当前安装结果。** 这些区分比背熟命令有用。

适合的工作： 跨多次会话的行为变更；旧系统里边界容易被误改的小改动；需要需求、设计、任务一起评审的协作；中断后需要准确恢复的工程任务。不适合指望它独自完成的工作： 没有代码与环境访问的根因定位；丢包、抖动、A/V 同步的实测结论；硬件音频链路与调度时序保证；替代代码评审、CI、灰度或发布审批。

本文做的是只读研究。获取了完整仓库快照并逐 blob 校验，但只精读和定向检索了与报告有关的 45 个文件；十二项工作流入口全部核对，不冒称十二份长正文全都读完。后文所有手机、会话、音频与弱网案例均为教学假设，没有读取用户项目，没有执行上游代码，没有性能实测。

两套规格不是重复劳动

仓库内常见的 openspec/specs/ 是被维护的主规格；openspec/changes/<name>/specs/ 是某次变更相对主规格的差量。主规格回答“当前接受的行为是什么”，delta 回答“本次打算增加、修改或删除什么”。这里的“当前”是一种维护约定，不是工具扫描代码后签发的事实证明：如果团队先归档、后遗漏实现，规格照样可能领先或偏离真实系统。getting-started.md L52–76 ↗

三、八个关键机制精读：哪些约束真能防止 AI 跑偏

1. Propose 的停止点：把“我要做”与“现在可以改代码”分开

官方约束： propose 只做规划。即使最初请求宽泛地包含“build”，也不能顺便实现；产物齐备后停止，实施需要新的明确请求。输入中关键行为含混要问清，非关键细节可记录假设；落笔前还应只读查看相关实现、测试、配置与文档。propose.ts L19–54 ↗ propose.ts L119–173 ↗

为什么有用： 模型往往把“理解需求”和“开始改代码”压缩成一次连续动作。显式停点让人能在实现成本产生前纠正行为边界。WebRTC 的“弱网后自动恢复”究竟恢复信令、媒体收发还是用户正在进行的语音轮次，差别很大；一句“理解了”不能替代可审查的场景。

反例与边界： 模板写了 STOP，不代表终端工具被物理禁用。宿主若配置自动执行，技能仍只能提供行为约束，不能自创权限；反过来，本报告也不会因为模板里有命令就执行它。若工程上下文不可见，应把规划标成待核实，而非生成看似精确的文件路径和类名。

2. Proposal 的能力清单：不是“要改哪些类”的漂亮目录

官方模板把能力分成 New Capabilities 与 Modified Capabilities。新能力要能长期容纳相关行为；既有能力只有需求变化才列入 Modified，并使用主规格已有的完整路径。纯重构、工具或文档变更没有能力差量时，应明确声明 skip_specs: true，而不是虚构需求去满足校验。proposal.md L11–29 ↗

分析： 能力是规格的组织单位，任务是执行单位。把 add-session-manager-class 当能力名，会让下一次改实现时误以为产品行为也变了；把 audio/session-isolation 当假设能力路径，则能跨内部实现稳定表达“旧会话音频不得泄漏到新会话”。这只是命名示例，不声称用户已有此目录。

4. 文件存在检查：断点恢复的地基，也是最易误读的信号

典型中断： proposal 列了两项能力，助手写完第一份 delta 就断开；下次 status 的 specs 可能已是 done。continue 模板因此先比对期望文件和 existingOutputPaths，必要时只补缺失文件，并把这次补齐算作“一项产物”，不立即继续狂奔。它还要求解析符号链接后确认路径仍在 changeRoot 内。continue-change.ts L19–22 ↗

5. Delta 的精确语法：可解析性换来工具协作，也引入替换风险

官方将行为差量分为 ADDED、MODIFIED、REMOVED、RENAMED。新/改需求使用 ### Requirement:，场景是恰好四级的 #### Scenario:，有 SHALL/MUST 和 WHEN/GIVEN → THEN 的可观察语义。新能力的 Purpose 要有足够说明；既有能力的 Purpose 不由 delta 任意覆盖。schema.yaml L96–125 ↗

最关键约束： MODIFIED 不是“只写新添的一句话”。schema 明确要求从主规格复制完整需求块及场景再修改。机械合并路径会替换完整块，当前代码还会检查旧场景名是否丢失。忘了已有“正常结束”的场景，只留下“弱网恢复”的场景，不是精简，是可能抹去已有契约。schema.yaml L127–134 ↗ specs-apply.ts L549–578 ↗

不要过度相信语法： 保留场景名却把 THEN 从“不得播放”改成“可以播放”，文本结构仍可能合法；规则能发现一部分损失，不能替人判断行为退化。重命名需求也不必重命名代码符号，verify 模板特别区分了这两件事。verify-change.ts L97–114 ↗

6. Tasks 把验证写进每一项，而不是最后挂一个“全部测试”

schema 要求 checkbox 任务足够小、可验证，并在每个任务中写清验证方式；不要把所有测试、文档一股脑推到最终任务组。完成标记只认 x/X。归档后再做的建议可用普通列表保留在跟踪范围外，但这不授权助手把本应交付的行为偷偷挪成后续工作。schema.yaml L210–237 ↗

分析： “完成 session 隔离”是一张许愿清单；“让旧会话回调被拒收，并以确定性调度测试覆盖中断前后两种到达顺序”才同时给出接缝和证据。任务不必强制某个测试框架，但必须让复核者能问：你凭什么打勾？设备依赖暂不可测，就写未验证与后续条件，不拿本地单测代替音频链路验证。

注意： OpenSpec 没有因此自动实行 TDD。它组织任务和证据要求；先写失败测试、确认失败原因、最小实现、再重构，是另一套可组合的工作纪律。若采用 Matt 的 tdd，也应只在有可控输入输出的接缝使用，而非凭 Markdown 场景假装已构建真机可重复实验。

7. Context、Rules、Operation guidance：三种输入不能互相冒充

config.yaml 的 context 为项目事实与约束；rules 按产物注入，例如 specs 的行为表达规则；operations.apply/archive.guidance 是执行操作的建议。instructions 返回的模板、依赖和路径则来自当前解析的工作流。官方明确说这些 prompt-level 输入不是可强制执行的检查，也不能覆盖 CLI 状态、路径和用户选择。customization.md L75–129 ↗

为什么要分： “我们的音频线程不能阻塞”是背景约束；“每个场景给出可观察结果”是规格写作规则；“先跑窄范围测试再跑全套”是操作建议。如果把“所有任务都可以算完成”塞进 guidance，就能覆盖 blocked 或进度，那工具返回的事实失去了意义。当前 apply 模板要求遇到冲突报告并保留控制值。apply-change.ts L78–101 ↗

安全推导： 私有代码可以仅存在本地，AI 助手是否把所读内容送往外部服务，取决于宿主与组织配置，不能由“本地 Markdown”推出“数据不出网”。应避免在公共可提交的 context 中存凭证、客户日志和个人信息；这属于工程使用建议，不是 OpenSpec 自动提供的脱敏能力。

8. Apply 是动态读任务，不是执行一份不可变的旧计划

apply 先查 status，再取 instructions apply --json，读返回的所有 contextFiles；按当前任务位置实施，每次打勾前核对 sourcePath 与 line 仍指向同一描述，打勾后刷新 instructions。遇到设计问题、范围扩大或试图缩减既定行为，都应暂停，而不是静默妥协。apply-change.ts L47–76 ↗ apply-change.ts L93–127 ↗ apply-change.ts L189–205 ↗

源码边界： apply 的硬阻塞主要检查 apply.requires 指定的直接产物是否存在；另返回传递缺失项 missingPrerequisites。它不是把整个规划闭包逐项语义认证后才解锁。默认 tasks 存在但 specs 缺失的异常状态，不能被描述成“引擎绝对不允许开始”。规划模板额外遍历依赖闭包，就是在弥补这类文件状态的局限。instructions.ts L558–585 ↗ instructions.ts L631–679 ↗ ff-change.ts L85–93 ↗

分析： 这种每次回读比依赖聊天记忆稳，但引入 I/O、上下文和审查成本。它保护的是“我现在正在执行哪一版任务”的一致性，不是媒体线程上的内存一致性。会话重开后的恢复能力与工程系统的并发正确性，是两类完全不同的问题。

五、同步与归档：两条不同路径，以及不能跳过的失败语义

智能 sync 与机械 merge 的分界

openspec-sync-specs 说明自己是 agent-driven direct edits：助手读取 delta 与主规格，智能合并，尽量保留未提及的内容和场景。它把 ADDED 撞上既有需求视作隐式修改；缺失 MODIFIED/RENAMED 的基线则阻塞。它从 status 的具体输出列表选取 delta，而不是遍历任何看起来像规格的 Markdown。sync-specs.ts L13–23 ↗ sync-specs.ts L47–68 ↗ sync-specs.ts L103–122 ↗

直接 CLI openspec archive 的差量应用在 specs-apply.ts 中有确定的操作序列：RENAMED → REMOVED → MODIFIED → ADDED。MODIFIED 替换完整需求块；ADDED 遇到同名但不同内容会报冲突，而不是自由推断怎样揉在一起。某些已经应用且一致的操作可成为 no-op，但这不等于任何重复执行都能无脑重试。specs-apply.ts L461–608 ↗

实际后果： 不能用“智能 sync 会保留未提及内容”来为不完整 MODIFIED 辩护，然后又换成机械 CLI 归档。也不能看到 CLI 有保护检查，就以为 AI 直接编辑主规格时拥有同等代码级保证。复核记录应写清用了哪个入口、主规格差异是什么，而不只写“已同步”。

archive 技能先看产物和任务；产物不齐或任务未完会警告，但用户可确认继续。也允许明确选择不更新主规格就归档。正式移动前会检查日期前缀和归档目标，目标已存在应在写主规格前停止；请求同步时必须在当前流程内完成并确认结果，不能后台发起后立刻移动。archive-change.ts L87–129 ↗ archive-change.ts L146–204 ↗

CLI 也不是“只接受所有 checkbox 全绿”：--yes 可越过未完任务的确认；--skip-specs、--no-validate 有各自语义，不能将它们当常规提速套餐。代码会预留归档目标，保存规格快照并在部分异常下回滚；但存在回滚分支不等于具备数据库级强事务。archive.ts L1595–1683 ↗ cli.md L669–758 ↗ archive.ts L822–850 ↗ archive.ts L2275–2306 ↗

官方 agent contract 写得很直接：archive: null 表示失败，“This is not a guarantee that files are unchanged.” 回退移动、清理或回滚本身可能失败。处理此类错误应先保留并检查活跃变更、归档目录和受影响主规格，再决定恢复；不要看到失败码就立即重复归档或删除恢复路径。agent-contract.md L79–84 ↗

归档是知识维护，不是“已上线”

归档把一次工作从活跃变更区移走，主规格是否更新取决于所选路径。它不因此证明代码已合并、二进制已交付、实验已通过，或与当前设备镜像一致。OEM 可另将版本号、评审单与测试记录关联进产物；这是团队补充的追溯制度，不是 OpenSpec 自动建立的发布证明。

六、端到端假设案例：切网重连后，已打断的旧轮次音频又播放

场景声明与第一轮问题

以下完全是假设案例，不是用户项目诊断，不对应某个已复现缺陷。 设想一款手机语音交互应用使用 WebRTC 媒体通道：用户打断旧轮次 A 并开始 B，切网重连后，旧 A 的迟到音频又进了播放链。需求是隔离旧轮次，不是“一切声音都清空”。我们没有源码、日志、WebRTC 版本、线程模型或设备信息，因此不能认定问题一定来自 jitter buffer、session id 或哪个回调。

Delta 示例：完整保留原有场景，再增加中断场景

以下模拟一个已有需求块的 MODIFIED 结果，其中“正常轮次播放”是假设基线已有场景，“已中断轮次拒收”是新增场景。它不是只补两个场景的局部补丁；真实使用必须从项目主规格复制完整原文后再改。本示例未提交、未经过 OpenSpec 命令校验。

# Spec Delta

## MODIFIED Requirements

### Requirement: Turn audio output
播放系统 SHALL 仅输出当前有效轮次允许的音频，
并拒绝已确认中断轮次随后到达的音频。

#### Scenario: Active turn playback
- GIVEN 轮次 B 处于有效状态
- WHEN B 的合法音频到达播放边界
- THEN 系统保持 B 的正常播放能力

#### Scenario: Interrupted turn rejected
- GIVEN 轮次 A 已被确认中断且 B 已开始
- WHEN A 的迟到音频在切网重连后到达播放边界
- THEN A 的音频不进入可听输出
- AND B 的有效音频不因本次拒收被一并丢弃

为什么不写“加 generation 校验”？ 因为那回答怎么做，可能把错误机制提前固化。真正应评审的是：哪个时点构成“确认中断”，播放边界如何观测，已经送达底层硬件但尚未听见的片段是否包括在承诺内。如果产品期待“瞬时绝对静音”，却没有定义测量边界和物理能力，Markdown 再严格也只是不可检验的口号。

Design 与任务：列替代方案，不假装知道源码接缝

此任务涉及生命周期与异步边界，值得写 design。候选方向可以是：轮次标识贯穿接收至播放、集中管理有效性、在队列边界取消旧工作。每个方向都要讨论已入队音频、回调乱序、对象复用、锁竞争、恢复时 B 的连续性，以及如何回滚。这些仅为设计候选，不是本报告推荐某段生产实现，更不是根因判断。

任务不写“1改代码，2测试一切”。可形成下列假设清单：T1 固定当前正常轮次的特征测试与日志边界；T2 建立可控回调顺序的测试接缝；T3 覆盖 A 中断前后迟到音频与 B 正常输出，并随实现给出确定性测试；T4 覆盖重连与中断交错的集成路径；T5 在具备条件的设备与网络环境验证可听行为并留存脱敏证据。每一项都写通过条件，缺设备的 T5 不能被 T3 通过抵消。

这里可以只对 T3 的状态逻辑采用 TDD，而不是为整条真实媒体链路承诺一个“全绿单测”。若调查发现旧代码不可隔离，先做保持行为的测试接缝或缩小变更，不能为了过测试把“不得复播”改成“大多数时候不复播”。

实施、验证和归档分别给什么授权

审阅并批准规划后，另发 /openspec-apply-change isolate-interrupted-turn-audio，并明确实施范围与可运行的测试。助手遇到现有结构与规划冲突，应暂停提出修订；可用 /openspec-update-change 调整既有产物，并重新确认行为变化，不能先改验收条件再宣布完成。

实施后先看 CLI 规格检查的 issues，再看已启用的 verify 技能输出；最后审阅实际运行记录。真实项目中可请求：

/openspec-verify-change isolate-interrupted-turn-audio
分别列出需求→实现位置→测试/设备证据。
把没运行、没设备、没法观测的项目列为 Not verified。
本次只审查，不改代码，不打勾，不同步、不归档。

预期报告不应只是“通过”。它可能写：静态对应关系可定位，单元证据待提供，真机网络切换未验证；因此不能宣称就绪。是否在已知缺口下结束或拆分工作，是用户的明确决策。归档请求则独立给出，说明是否同步主规格、未完事项如何处理；本报告没有代发任何这些操作。

反事实检查：如果只是音频模块重构呢？

若目标只是拆分过大的模块，所有可观察行为保持不变，就不该编造一个新规格变化。先保护既有行为、记录设计与任务，并显式使用适用的 skip_specs 元数据。反过来，“只是重构”不能掩盖线程调度和可听行为变化：一旦更改中断、超时或重连语义，就回到行为 delta 审查。这条界线由证据决定，不由提交标题决定。

第二步：只审一份规划。 用 propose 建立意图、差量、必要设计和可验证任务；亲自读能力路径、非目标、保留场景、未决问题。习惯更细粒度时才改用 new + continue，不是把两条规划路径都跑一遍。先量化“有没有遗漏关键场景”这类可解释结果，不杜撰节省了多少小时。

九、失败模式与代价：没有上下文，规格也能写得非常自信

规格可能只是被持久化的误解。 需求写得明确不代表它正确；AI 若没有读实现、配置与现有测试，可能建立一个内部自洽但与产品完全不同的模型。OpenSpec 把误解暴露到可审查文件里，这是机会，不是自动纠错。不要让“文件齐了”减少对需求内容的审查。

反复回读会消耗上下文与时间。 proposal/spec/design/tasks 分开有利于责任清晰，却也会重复背景、放大过时信息。长任务清单不如小范围、每项可验证的清单。官方建议保持上下文卫生，但清空聊天后仍要把仓库事实与已确认决策读回来，而非期待“清空就更聪明”。README.md L217–221 ↗

并行改同一能力仍会冲突。 A 添加一个场景，B 用旧基线修改同一需求：CLI 可能挡住场景名丢失，智能 sync 可能保留未提及内容；但两者都不保证业务意图兼容。两份 delta 都保留名称却互相反转 THEN，结构检查无法替代跨变更评审。批量归档也不应该被当成不看主规格 diff 的理由。

强流程可能压过真实问题。 一行明显错误的日志文案不一定值得四份长产物；不影响行为的重构不该编造差量；完全未知的设备故障应先取证而非先定规格。可以缩小产物、选合适路径；如果必须每次都解释为何流程不适用，说明切入点或定制方式可能不对。

归档和验证都是可被人为绕开的约定。 archive 允许警告后继续，任务勾选也由助手或人写文件。要求强保证的组织必须在 CI、评审和发布系统设门禁，不能只写“永远运行全部测试”。本报告没有评估上游整个安全面，也没有证明任何一个宿主会严格遵守模板。

离线材料不代表离线工具。 OpenSpec 有默认开启、可退出的匿名遥测；源码当前发送命令名、版本、surface，并使用匿名标识及事件时间，$ip: null。发送受启用状态和提示已显示等条件控制。环境变量 OPENSPEC_TELEMETRY=0 或 DO_NOT_TRACK=1 可退出；本地关闭遥测并不控制 AI 宿主本身的网络行为。不要把“官方说匿名”写成“绝无隐私风险”。index.ts L65–100 ↗ index.ts L129–184 ↗ opt-out.ts L12–29 ↗

十、读完之后该保留的判断，以及本稿核验边界

如果只保留一个判断标准：一次变更能否让未参与聊天的工程师，仅凭规划、代码与证据，知道承诺了什么、改了什么、哪些仍未知？ OpenSpec 的目录、delta、schema 和技能围绕这个目标提供协作骨架。它最有价值的结果不是更多 Markdown，而是让歧义、遗漏和不充分证据更早显形。

对 WebRTC 工程，不要先问“能否全自动”，先问三件事：第一，是否把用户可观察行为与候选机制分开；第二，是否保留原有场景并覆盖异步边界；第三，真实验证是否与规格和任务相连。回答不清楚，继续扩大流程通常只会把问题包装得更工整。

本稿范围： 官方身份交叉核对；固定提交的完整树与 1384 份 blob 快照；45 个文件的精读或定向检索；12 项工作流入口地图；四份默认模板、schema、关键状态/合并/归档/验证实现。范围与行段详见本地 source-ledger.md 和 source-coverage.json。没有逐文件审计全部源码、测试、网站、适配器与依赖，没有独立核验发布二进制或在线 npm 制品。

本稿没有做： 安装启用技能、执行上游 CLI 或脚本、跑上游测试、读用户项目、真机实验、发送消息/邮件、公开发布、调用付费服务或登录。离线 HTML 的静态检查与交互逻辑检查不等于真实浏览器渲染验收；主笔还需抽核行号证据并在手机/桌面实际打开检查。可折叠正文用于分层阅读，不隐藏重要安全结论；打印按钮会展开全部内容。

优先独立复核： 2.1.1 的安装作用域与离线边界；默认 DAG 与存在性状态的区别；智能 sync 和机械 archive 的语义差异；验证三层与缺证据不就绪；归档非强事务、Stores 不自动路由。它们是本篇最容易被简化成错误宣传、也最值得沿原文验证的五组事实。
