十分钟主线

01 · 十分钟主线：让下一会话有依据地继续

长任务 Agent 的难点不只是“能想多久”。一个会话改完代码后，下一个会话要知道需求还剩什么、哪些结果可信、环境能否复现，以及发生中断后该从哪里继续。Anthropic 的文章给出一套针对全栈 Web 开发的交接办法。它不是无人值守生产系统的完整设计。

原文由 Justin Young 撰写，页面标注 2025 年 11 月 26 日。本讲义于 2026 年 11 月 21 日，北京时间核读。原文讨论 Opus 4.5 的实验经历。配套示例固定在另一时点的仓库提交，不应把示例默认模型与文章实验模型混为一谈。[1][2]

  1. 先定义“做完”是什么。初始化会话把需求展开为带用户操作步骤的功能清单，所有 passes 初始为 false。目录、页面和代码文件存在，不构成产品完成。
  2. 后续会话只推进一个可验证功能。先读规格、进度和 Git，再启动环境、复测核心路径，之后才写新功能。目标是交出可接续的小改动，而不是让每个会话重新造整个应用。
  3. 把交接信息留在模型之外。feature_list.json 保存需求状态，claude-progress.txt 解释当前进展，Git 保存已提交代码，init.sh 描述环境启动。这些材料分工不同，不能互相替代。
  4. 测试必须经过真正会失败的链路。文章中的浏览器操作补上了“接口返回成功，但用户用不了”的缺口。对手机 OEM 项目，浏览器测试依然不能证明设备权限、音频路由或底层库行为正确。
  5. 不要把提示词当强制协议。示例让模型遵守“只改 passes”，但所读编排代码没有检查功能清单语义差异。进度函数统计 JSON 标记，不执行测试。恢复入口看文件是否存在，不验证初始化是否完整。
  6. 超出本地代码后，还要补恢复协议。检查点必须绑定版本与证据。外部请求超时要表示“结果未知”，不能直接解释成失败并重发。Git 回退不会撤回远端任务。本讲义后半部把这些补充逐项展开，均不是原文已经实现的能力。

这篇讲义给你的设计判断

如果你正在让 Agent 改造一个有前端、后端和测试环境的项目，先采用文章的单会话单功能与交接材料，再按风险补强。若任务只是一处可在一个窗口内验收的小改动，不必先建数百项功能表。若任务会刷机、修改生产配置或启动远端任务，不能只复制这个 quickstart。

阅读分层：前 1–10 章解释原文与源码。第 11–16 章主要是带前提的工程设计补充。每一章都标明依据。全文是 Explanation，用于理解机制和选择方案，不是已经运行成功的部署教程。

02 · 两类主要失败，不是同一种记忆问题

原文 第一类是一次做得过多。模型试图一次性完成应用，窗口耗尽时停在半成品中间。下一会话看不到清楚的交接，只能猜改动意图，甚至先花大量时间修复基础运行。上下文压缩没有消除这个问题，因为压缩结果不一定保留足够清楚的操作指令。[1]

第二类发生在已有一些功能之后。新会话看到应用有了外观和部分行为，就宣布整个任务完成。这里不一定缺少关于过去的事实，更可能是缺少一个无法随意缩小的“完成范围”。继续扩大窗口不会自动修复验收标准。

原文后面又补了两个具体症状

模型会在没有充分测试时把功能记为完成，也会反复琢磨如何启动应用。前者需要端到端测试与完成约束，后者需要启动脚本与明确交接。原文末尾因此列出四行问题表，但开头概括的是两种主要失败模式，不是“四个并列研究结论”。

失败真正缺少什么只加日志为什么不够
中断后无法接续可恢复的代码边界、剩余事项与验证方法“实现到一半”没有指出哪部分可信，也没有指出能否启动
局部成功后提前结束需求全量范围与逐项验收日志只讲已经做的部分，不会自动列出漏做需求
未经充分测试就打勾与版本绑定的用户行为证据“测试通过”是一句话，未说明跑了什么、在哪个版本上跑
每轮重新探索启动方式可重复执行的环境入口写在历史聊天里的命令不一定能在新环境中工作

证据到哪里为止

文章说这些做法在内部实验中提高了表现与效率，但没有给出可复算的对照数据、样本量、成功率区间或全套实验产物。不能据此写“成功率提升多少”或“任意长任务都能可靠完成”。作者明确说，单个通用编码 Agent 与更多专门 Agent 哪个更好，仍是开放问题。

03 · 贯穿项目：实验室任务台，而不是生产终端控制器

虚构案例，教学假设 假设你要做一个“设备回归任务台”。前端展示实验室设备，用户选择测试配置、创建回归任务，查看状态和报告。服务端保存任务，并调用一个虚构的实验室执行服务。任务包含一个既有音视频用例，但这里不讨论其传输协议。

我们假设前后端代码在同一工作目录，测试数据库可重建，只有一个编码 Agent 写代码。实验室执行服务独立于代码仓库。它有创建任务与按业务请求标识查询的接口。后文会分别讨论它支持幂等和不支持幂等的情况。所有运行轨迹、编号和时间点都是构造的，没有在真实设备或服务上执行。

需求标识用户可见的完成条件容易误当成功的现象
F01 设备列表打开页面后能看到确定的测试设备，空列表有说明写了设备卡片组件，但数据请求失败
F02 创建任务选择配置并提交后出现任务详情，刷新仍能找到按钮弹出成功提示，但任务没有持久化
F03 请求去重同一业务操作的重复请求不多建任务，主动新建不被误去重前端禁用按钮，但网络重试仍创建两份
F04 结果展示已完成任务显示对应报告，失败任务不显示伪成功仅根据 HTTP 200 显示绿色状态
F05 状态恢复重启服务后任务记录仍可查询，远端状态未知时明确显示页面保存了上一屏截图

为什么先把项目边界写窄

Agent 若把“设备回归任务台”理解成“可自动刷机和控制全部测试设备的平台”，就会把交付范围和权限一起扩大。规格应先写明：本次只连接隔离的测试执行服务，不包含固件更新、生产设备、付款、通知或对外发布。能力可达不等于有权执行。

这个案例故意包含一个远端副作用，目的是解释文章方案的边界。文章的 Web 开发经验并没有给出远端任务去重、断电恢复或真实手机测试的实现。后文的这些设计都属于本讲义补充，不能算作 Anthropic 原文已经验证的结果。

04 · 初始化会话写的是接续条件，不是完整产品

原文 初始化会话创建启动脚本、进度文件、功能清单和初始 Git 提交。后续编码会话再逐项推进。这两个“Agent”的区别主要是初始用户提示不同，原文脚注说明系统提示、工具集合和其余运行框架相同。它们不是必须同时运行的两支独立服务。[1]

固定提交源码 initializer_prompt.md 要求先读 app_spec.txt，再生成至少 200 个带步骤的功能测试条目，包含 functional 和 style；至少 25 项有 10 步以上。所有 passes 初始为 false，再创建 init.sh、初始化 Git 与项目结构。若有剩余时间，可以开始最高优先级功能。[3]

200 是示例设定，不是最佳实践定律

原文提到 claude.ai 克隆案例有 200 多项功能。示例 README 也说明可以为更小演示降低数量。把一个小项目机械拆成 200 项，会增加重复项、阅读成本和维护成本。覆盖度应由需求与风险决定，不由条目数决定。对虚构任务台，F02 可以细分为参数校验、提交、持久化、刷新和错误反馈，但不应该把每一种按钮颜色都计为新的业务能力。[2]

初始化产物下一会话依赖它回答的问题缺失时的后果
功能清单哪些可观察行为尚未通过靠页面外观判断进度，遗漏后台和异常路径
init.sh如何启动正确版本的应用与依赖同名端口上跑着旧服务，测试了错误实例
进度说明上一轮做了什么、还有什么风险把实验性代码当成稳定实现
Git 基线哪些代码属于可回退的已知状态无法区分已有改动与新一轮产生的改动

初始化本身也会中断

如果 Agent 写出了 feature_list.json 的前半段就退出，文件“存在”不代表 JSON 可解析，更不代表脚本、Git 和进度都准备好。初始化不是零风险阶段。教学设计应把“准备中”和“已验证可接续”分开。后文会看到，示例编排并未替你完成这个校验。

教学补充

一个更稳的初始化完成判据可以是：规格版本固定、清单可解析且覆盖已审需求、启动脚本在隔离环境通过一次健康检查、初始提交可识别、进度说明存在。最后由程序写出带内容散列的 ready 记录。它是本讲义建议，不是上游代码已有逻辑。

05 · 功能 JSON 是需求账本，passes 不是测试引擎

原文 每项包含类别、描述、用户操作步骤与 passes。作者说在他们的实验中，模型对 JSON 的不当改写比 Markdown 少，因此使用 JSON。这是经验判断，不等于 JSON 天然防篡改。[1]

下面沿用上游四字段形式，但内容来自虚构项目。它是教学示例，未执行。步骤必须让下一会话知道操作对象和观察结果，而不是写“测试创建任务功能”。

[
	{
		"category": "functional",
		"description": "F02 创建任务后刷新仍可查询同一任务",
		"steps": [
			"以隔离测试账号打开设备回归任务台",
			"选择设备 LAB-01 和配置 profile-A，点击创建",
			"记录详情页显示的任务标识",
			"刷新页面，再查询该标识",
			"核对设备、配置和任务标识均未改变"
		],
		"passes": false
	}
]

只改 passes 的规则到底保护什么

这条规则防止实现者通过删除难项、放宽步骤、重排优先级来制造进度。coding_prompt.md 明确禁止删除测试、修改描述和步骤、合并或重排条目。但这些禁令是发送给模型的提示，不是所读 Python 代码中的结构化差异校验。模型同时拥有 Write 和 Edit 工具，具备修改整个文件的能力。[4][6]

还有一个容易漏掉的细节：初始化提示强调只允许从 false 标为 true，编码提示却明确要求在启动复测发现回归时立即标回 false。因而不能把整套示例概括成“通过状态永不后退”。工程上，历史曾通过与当前仍通过是两种事实。一次代码变更后旧证据失效，状态就需要重新验证。

需求确实写错了怎么办

禁止 Agent 偷改验收，不等于永远不允许需求变更。若规格把“提交后立即完成设备回归”写成必过条件，而回归本来需要异步执行，应停止该项，把冲突交给有权决定范围的人。批准后形成新的规格版本与变更说明，再重新生成或迁移相应验收项。静默删除失败项会污染分母，旧版本的通过率不能与新版本直接比较。

教学补充

生产设计可以把不可由编码 Agent 改写的 requirements.json，与执行器维护的 results 分开。结果记录 requirement_id、spec_hash、code_revision、环境与运行编号。状态采用 unverified、running、passed、failed、blocked；只在展示时折算“已通过”。拆文件本身不形成隔离，写权限也要分开。

06 · 固定源码揭示的真实会话循环

源码核读 本轮从原文中的 quickstart 链接追到 anthropics/claude-quickstarts/autonomous-coding，通过 cursor-github 只读工具固定提交 4a4224bdf0e9cfb3332167b69c90457403813625。这是核读时 main 指向的仓库快照，不声称它就是 2025 年文章发布当天的代码。仓库提交时间为 2026 年 11 月 7 日 03:37:53，北京时间；该提交的变更属于其他示例，不代表 autonomous-coding 在该日被改写。[9]

五个应当知道的实现细节

  1. run_autonomous_agent 只用 not tests_file.exists() 判断首次运行，不检查清单 schema、初始化提交或进度文件完整性。部分初始化也可能被当成续接状态。
  2. 首次提示发出前，进程内 is_first_run 就变成 false。初始化会话异常后，同一个进程的下一轮仍选 coding 提示。退出后重启则重新看文件是否存在。两种恢复路径不完全相同。
  3. run_agent_session 正常读完响应就返回 continue；它不解析“完成”声明，也不把工具失败自动升级为整个任务失败。工具结果错误会打印，但正常结束仍能返回 continue。此处是静态控制流观察，不是对 SDK 所有异常行为的运行证明。
  4. 循环的明确退出条件是迭代上限。该文件没有根据全部 passes 为 true 自动 break。输出文案中的“until completion”不能替代实际分支。
  5. 代码为自动续接设 3 秒等待，并有额外会话间延时。它没有在此实现失败类别、重试额度、指数退避、总费用上限或相同错误熔断。把演示直接改成长期服务会引入成本与重复失败风险。
[5]

版本名字不要混用

文章讨论 Claude Agent SDK 与 Opus 4.5。快照代码导入的是 claude_code_sdk，入口默认模型是 claude-sonnet-4-5-20250929。client 设置 max_turns=1000，并配置 Puppeteer MCP。这里描述的是该快照的文本，不是 2026 年最新 SDK 的接入指导。不能据此推导当前包安装方式、可用模型或服务价格。[6][8]

安全 hook 并不负责验收真伪

client.py 写出 sandbox 与项目目录文件权限设置，并将 bash_security_hook 接在 Bash 的 PreToolUse 上。security.py 检查命令允许列表及少量特定命令参数。这里没有给 feature_list 的语义变更或“是否真的通过测试”建立守卫。更不能因为源码写了 sandbox enabled，就宣称本轮验证了隔离效果。我们没有运行 SDK、命令或浏览器工具，也没有做安全审计。[6][7]

07 · 开始新会话，先证明基线没有坏

原文与提示 新会话查看目录，阅读进度、Git 与功能清单，选择未完成功能。作者又要求先启动开发服务器并测试核心功能。配套编码提示更具体：先复测 1–2 项已标记通过的核心功能；发现功能或视觉问题先修，再加新功能。[1][4]

为什么先复测，而不是相信上轮绿灯

上轮提交后，进程可能已退出，数据库可能仍是脏数据，端口可能被旧版本占用。若新功能建立在已破坏的基线上，后续失败就难以归因。先跑冒烟测试能缩小问题范围：故障若在本次编辑前已出现，就不是新改动首次引入。但只有 1–2 项核心复测，不构成完整回归覆盖。

接手问题虚构任务台的核对方式失败时的处理
我操作的是哪个版本页面构建标识与待测提交一致，服务指向隔离数据库版本不一致，先修环境，不写新业务
上次提交是否仍可运行F01 可加载，已有任务详情可打开标为基线故障，保留现场后修复
当前工作区是否混入他人改动核对未提交差异和来源不能归属的改动不覆盖、不自动清理
外部状态是否与日志一致按请求标识查询远端任务未知状态进入对账，不重建同一任务
本轮是否足够完成并验证选一个可在剩余预算内关闭的功能缩小实现单元，不压缩必要测试

init.sh 应当是可理解的入口

文章把启动脚本用于减少重复探索。教学上还应审查它是否会重复装依赖、重复创建样本、占用新端口、覆盖配置或清空数据。一个“每次都初始化数据库”的脚本能让首次演示成功，也能在续接时毁掉你需要诊断的记录。脚本名叫 init 并不保证幂等。

教学补充

把环境准备拆成依赖检查、开发服务启动、健康检查、显式测试数据重置。默认启动不做破坏性重置。记录启动的进程归属与版本，关闭时只处理自己启动的测试进程。此处解释设计目的，不提供可直接操作真实设备的命令。

08 · 一次一功能，单元应按可验证行为切分

原文 编码会话一次做一个功能，结束时留下可接续的干净状态。作者所说的 clean state 是接近可合入主分支的质量：没有重大 bug，代码有条理且有说明，下一人不必先收拾无关问题。它不是 git status 为空这一项指标。[1]

“一个功能”也不是“改一个文件”。在任务台中，F02 的可交接单元可能同时涉及提交表单、参数校验、数据库写入和详情页。若只完成按钮和假成功提示，虽然改动小，却没有形成可检验的行为。反过来，把创建、调度、报告、通知全塞进一轮，又会回到一次做得太多的问题。

依赖决定顺序，不只是清单行号

F04 结果展示依赖稳定任务标识与查询接口。若基础不存在，就先建立“创建一条任务并能查询”的纵向路径。对 F03 请求去重，应先明确相同业务操作的身份与存储约束，再补 UI 防重复。把去重仅作为最后的页面优化，会掩盖远端重复执行风险。

切分方法收益反例与修正
按文件或技术层切分容易分配工作和检查差异只写前端无法验证持久化。至少加能贯通的测试替身接口与明确限制
按用户行为纵向切分每次能展示可观察结果范围过大时按正常、失败、恢复场景拆开，但不把未测异常伪称已覆盖
按风险先做可行性验证尽早暴露外部服务或设备限制验证产物可能不可交付，应明确“验证性代码”与“可合入实现”的区别

结束条件比开工口号有用

本轮结束时，应能指向具体需求、代码差异和测试结果，并说明剩余事项。若实现没写完，允许留下明确的 work-in-progress 记录，但不能同时宣称基线可交付。涉及失败实验的修改需要隔离或按既定流程撤销，不能以“反正有 Git”自动覆盖共享工作。

教学设计可预留固定的收尾预算，供复测、整理证据和交接使用。这里不指定通用百分比，因为环境启动、设备测试与代码复杂度不同。预算不足时提前交接未完成事实，比最后几步省掉验证更可信。

09 · 端到端测试验证用户链路，不证明所有性质

原文 作者看到模型在做过单元测试或 curl 请求后仍遗漏端到端问题。显式要求用浏览器自动化像人一样操作后，模型更能识别并修复这些问题。文章也给出工具盲区：当时 Puppeteer MCP 下，模型看不到浏览器原生 alert 弹窗，依赖这些弹窗的功能更容易出 bug。这个例子是当时工具组合的观察，不应当成所有浏览器自动化的永久限制。[1]

“HTTP 200”为什么不等于 F02 通过

后端返回 200，只说明某次请求获得了该状态。前端可能把请求发到旧实例，渲染时读取错字段，也可能只在内存里保存结果。F02 的验收必须实际点击、记录任务标识、刷新、再查并核对。若环境使用假服务，要写明测试的是“前后端与假服务集成”，不是实验室执行链路。

截图证明了什么

截图能支持“在这个时刻、这个视口看到这些内容”，但不能单独证明请求只执行一次、状态已持久化或日志无敏感数据。对于 F03，还需要业务请求标识、任务表和远端任务计数的关联证据。UI 显示一个任务不等于远端只创建一个任务。

断言合适的检查证据不能越界的地方
刷新后还能找到任务UI 刷新后按同一 ID 查询，核对后端记录不能证明机器断电后仍持久化
重复请求不重复创建同一业务标识发起重试，查询唯一任务与远端执行记录按钮禁用或页面只展示一条都不够
错误状态没有显示为成功注入可控错误，检查 UI、数据库和错误分类一次 500 不覆盖超时已执行的未知状态
手机操作可用目标 WebView 与触屏交互，实际权限及系统状态桌面浏览器缩窄视口不等于 OEM 真机测试

不要把示例的“全用浏览器”当通用测试原则

配套提示强调 ALL testing 使用浏览器，目的是纠正该演示只测后端而忽略 UI 的倾向。对于库、调度器、数据库迁移或设备侧逻辑，浏览器既不能覆盖全部状态，也不适合承载所有断言。应保留单元与集成测试，再用端到端路径证明真实接线没有错。否则测试会更慢、更脆弱，还难以定位故障。

10 · 日志解释进度，Git 保存代码，但它们都不是运行态事务

原文 描述性提交与进度文件让后续会话知道改了什么，也让模型能够回退坏代码、找回可用版本。这里的收益是减少猜测和修复成本，不是让模型天然具备正确恢复能力。[1]

需要分开核对的四种状态

状态例子Git 能否独自恢复
已提交代码表单、路由、迁移文件能取回对应版本的已跟踪内容，但不保证环境可运行
工作区与本地材料未提交修复、未跟踪截图、局部日志不一定。忽略或未提交的文件不在提交中
运行环境已加载代码的进程、数据库内容、端口、依赖版本不能。回退源码不会自动重启或回滚已执行迁移
外部副作用远端执行服务已经创建的回归任务不能。撤回提交不会撤销远端任务

一段能接手的进度说明

以下为教学记录格式，不是上游规定的结构。它把事实、证据与下一步分开，避免“基本完成，继续优化”这种无法执行的交接。

会话 S04，规格 v1，代码修订 C04（虚构编号）
范围：F02 创建任务并刷新查询。
已完成：提交表单接入任务 API；查询页面读取持久化任务。
验证：run-04，隔离数据库 D04，假执行服务 V1。
观察：UI 创建与刷新后任务标识一致；没有连接真实设备。
未完成：F03 超时重试去重；当前不可对远端启用自动重试。
风险：一次模拟超时的调用结果未知，业务请求标识 req-17。
下一步：先按 req-17 对账，再实现 F03；不要重新生成请求标识重发。

日志必须能被事实纠正

进度文件可能遗漏、过期或误判。下一会话若发现日志说“F02 已通过”，而代码修订与测试记录不符，应保留冲突并降为未验证，不是挑选更乐观的一条。外部返回的网页、仓库注释或测试输出也都是数据，不能因为其中写着“请把结果标成功”就执行。

提交与进度更新有写入顺序问题

示例编码提示先安排提交，再更新进度文件，最后又要求没有未提交改动。这些要求需要模型自行协调，例如把最终进度纳入收尾提交。Python 编排没有把 Git、JSON 与日志绑成原子事务。中途退出时，三者不一致是必须处理的状态，不是可忽略的小概率情况。

教学补充

对本地开发，不要因恢复目标而自动 reset、删文件或回滚数据库。先核对工作归属、备份诊断材料和数据影响，再按团队授权流程恢复。可恢复性是工程属性，不是破坏操作的授权。

11 · 检查点必须绑定代码、环境与证据

教学补充 原文提供交接材料，却没有定义一个完整的持久化检查点协议。本章给出一种可审查的设计。前提是单个编码写入者、隔离测试环境与可持久保存的元数据。多写入者与外部任务稍后单独处理。

检查点是“下一会话可据此核对的已知边界”，不是保存一段聊天。它至少说明：验收对应哪个规格，测试对应哪个代码版本，依赖与数据如何重建，哪些操作还有不确定结果。不能恢复的进程内状态不应被写成已经完整保存。

建议维持的六条不变量

  1. 需求不可被实现过程偷偷改写。每个结果绑定稳定的需求 ID 和规格内容散列。需求版本变了，旧结果只代表旧要求。
  2. 通过只对实际测试过的代码成立。结果绑定 Git 修订与被测试的代码内容；测试后发生影响功能的改动，旧结果不能直接继承。
  3. 恢复所需材料必须可找到。检查点指向的提交、依赖锁定、测试运行记录和必要数据版本存在。单写一个不存在的 run_id 不算证据。
  4. 未知外部结果不能当失败。已发出但未确认的任务留在 pending reconciliation。下次先查询，不能重新生成业务请求标识再执行。
  5. 同一工作单元只有一个有效写入者。如果引入并发，每个写入者要有隔离工作区和结果汇合规则。仅靠“不要互相覆盖”的提示不成立。
  6. 收尾失败时不发布成功。保存检查点或证据失败，任务仍是未封存状态。内存里算出的通过结果不能冒充可恢复进度。

为什么不用一次覆盖多个 JSON 文件模拟事务

分别写功能表、日志和检查点，中途崩溃会留下混合版本。把单个文件写到临时位置再替换，能减少某些半写风险，但并不自动形成多文件事务，也不提供通用的断电持久化保证。若元数据一致性重要，可以把一次状态转移及其引用放进同一数据库事务；源码和测试证据仍通过内容引用在恢复时验证。

SQLite 的官方原子提交说明解释了回滚日志、写入顺序和刷盘对掉电恢复的作用，并明确文中机制针对 rollback mode，WAL 使用不同机制。文档还列出锁与存储刷写不可靠时的限制。它支持的结论是“持久一致性需要明确机制和前提”，不是“放进 SQLite 就没有任何恢复风险”。数据库事务也不会把 Git 或远端服务一起纳入事务。[13]

一个最小检查点记录

# 教学数据形状，未在本轮实现或测试。
checkpoint = {
	"spec_hash": "content-hash-of-reviewed-spec",
	"code_revision": "C04",           # 虚构编号，实际应为可定位修订
	"tested_tree_hash": "tree-hash", # 不包含运行时日志与证据目录
	"environment": "test-env-v1",   # 含依赖锁定与数据构造版本
	"verified_runs": ["run-04"],
	"unresolved_operations": ["req-17"],
	"next_action": "reconcile req-17 before new work"
}

这里允许检查点保存未决操作，是为了让中断后知道先做什么；它不意味着项目可交付。若检查点中仍有 req-17，系统可以安全地进入只读对账阶段，但不能对外声称 F03 已通过。

12 · 故障时间线：中断位置决定恢复动作

虚构推演，非实测 假设任务台正在实现 F03。C02 是此前验证过 F02 的代码修订，req-17 是一次已获授权的隔离实验任务的业务请求标识。所有 T 值只是事件序号，不是延迟测量。

新会话实际能知道多少

它能读到 C02 与尚未提交的 F03 差异，也可能看到发出 req-17 的持久记录。如果 req-17 仅留在已消失的上下文中，而服务又不能按调用者与关联标识查询，恢复者就无法可靠识别那个远端任务。进度文件写得再流畅，也不能重造丢失的关联关系。

因此，本例设计要求在发送前先持久记录业务意图和稳定请求标识。发送后没有确认，就保留 unknown。对账确认远端任务存在后，保存远端 ID，再重建本地展示和测试证据。若远端明确证明没有执行，才依据接口契约决定是否重试同一意图。

崩溃点看到的危险残留正确的恢复方向
初始化只写了半份清单文件存在但无法解析，启动脚本和 Git 都未准备进入初始化修复状态；不能因为 exists 为真就当作可续接
代码完成，测试未跑看起来合理的差异，passes 仍 false核对环境后执行测试，不因改动完整就置 true
测试已跑，记录未写上轮口头说成功，找不到运行证据重新验证，或恢复可信的独立运行记录
passes 已改 true，代码未提交状态领先于可定位的代码版本降为未验证，整理改动并在固定版本重新验证
提交已写，进度未更新Git 比文字说明新用差异重建事实，再测试；不要把过期日志当真相
远端已执行，响应丢失本地只有 timeout，没有远端 ID按稳定业务标识对账；无法核明时 blocked，不能盲目重放
检查点已保存，测试库被重置历史证据存在，当前环境已改变重建规定环境并复测；历史 passed 不等于现在 ready

恢复不是一律回退

回退代码只适合某些代码故障。它不能撤销 T2 的远端任务，甚至会让新旧数据格式不兼容。保留现场、向前修复、重新测试，往往比回退更适合本例。若确实要取消远端任务，取消本身也是有语义和权限要求的新操作，不能把它当作本地清理步骤。

恢复也不是从最后一行继续执行

“下一步调用创建接口”这句笔记如果写在请求发送之后，却在返回之前发生中断，照着继续就可能重复创建。恢复点应由持久状态与外部事实共同决定，不应由自然语言叙述位置决定。状态不清楚时暂停是有效结果，比伪造一个确定结论安全。

13 · 幂等让重试有条件成立，不让未知结果消失

外部一手参考与教学补充 AWS Builders’ Library 说明，调用者提供的稳定请求标识比“参数相同就算重复”更能表达意图。两个内容相同的创建请求，可能是一次操作重试，也可能是用户确实要两份资源。同一标识配不同参数，应拒绝参数冲突。去重记录有保留期限，晚到请求也必须纳入契约。[12]

用于任务台时，同一次“创建回归任务”的重试沿用 req-17。用户明确点击“再建一个相同任务”则是新意图，应分配新标识。每次网络尝试都生成新标识会破坏去重；只按设备和配置散列又会误吞用户主动创建的第二个任务。

客户端记录不能代替服务端去重

如果服务端先创建任务再写去重记录，正好在两步之间崩溃，重试依然会多建一份。如果先写“已完成”再创建，崩溃则会让一项从未执行的工作被当成完成。AWS 原文强调，去重标识记录与关联变更要满足原子、一致、隔离、持久的要求。跨多个外部系统时，本地数据库事务无法自动提供这种整体原子性。

若实验室服务只是把任务写入本地持久队列，可以在一个服务内事务中保存去重键、参数、任务 ID 与待处理记录。真正的设备执行仍需独立处理重复消费、失败与状态查询。不要把“任务创建幂等”推成“测试动作在现实世界只发生一次”。

教学伪代码：恢复时先对账

以下不是 quickstart 的代码，也未运行。它假设远端契约支持稳定幂等键、查询及足够的保留期。authorised_for 还要检查授权范围与过期时间。durable_tx 仅代表本地原子持久事务，不能把远端网络调用纳入其中。

def execute_or_reconcile(intent):
	# 教学伪代码，省略鉴权实现、连接和数据库细节。
	# key 绑定业务意图，不能在每次调用时重新生成。
	assert authorised_for(intent)
	with durable_tx() as tx:
		op = tx.get_or_insert_intent(intent.key, intent.params_hash)
		if op.params_hash != intent.params_hash:
			return BLOCKED("同一意图标识的参数已改变")
		if op.confirmed_result:
			return op.confirmed_result

	# 发出网络请求之前，意图已经持久存在。
	# 查询暂时不可用、不具权威性或处于传播延迟内，均不能证明没执行。
	observed = remote.lookup(intent.key)
	if observed.is_found:
		return persist_binding(intent.key, observed.result)
	if observed.is_unknown:
		return BLOCKED("等待对账，不重发新意图")

	if not contract_allows_safe_retry(intent):
		return BLOCKED("去重契约或保留期不足")
	try:
		# 服务端负责同一 key 的并发去重与一致性。
		result = remote.create(intent.params, idempotency_key=intent.key)
	except Timeout:
		persist_unknown(intent.key)
		return PENDING_RECONCILIATION
	return persist_binding(intent.key, result)

四个必须写进接口契约的问题

  • 去重键按账号、租户还是全局生效？跨环境是否隔离？
  • 重复请求返回原始结果、当前资源状态，还是可查询的关联标识？客户端分别怎么处理？
  • 同键不同参数如何报错？哪些参数算业务语义，哪些只是追踪字段？
  • 去重记录何时过期？客户端最长离线恢复时间是否超过这个期限？

服务没有幂等或可靠查询能力时，不要在 Agent 外面随手加无限重试。可以限制为人工核对、改造服务接口、改为先准备后明确确认的流程，或只允许无副作用的自动化。业务补偿也不是自动回滚：取消任务不能抹去设备已消耗的时间与已产生的观测结果。

14 · 选择方案要看任务长度、并发和副作用

教学比较 原文的优势是机制少，能把新会话拉回明确工作范围。它适合作为本地 Web 开发实验的起点。每补一层强约束，都要为存储、测试、权限和维护付成本。没有必要让每次小改动都依赖一个分布式工作流平台。

方案适用情况获得什么没有解决什么
单窗口完成并人工验收范围小、无跨会话要求实现成本低，审查集中窗口中断后仍可能需要重新梳理
文章式功能表、日志、Git多会话、单写入者、本地可重建项目减少范围漂移与交接猜测提示未强制、状态非原子、外部副作用未知
结构化结果与受控写入需求稳定、需要可审计验收防止静默改要求，证据绑定版本测试本身仍可能漏测，环境仍会漂移
持久工作流与服务端幂等长任务、会重启、涉及外部资源显式恢复、去重、对账与失败分类开发维护成本高，接口和存储契约复杂
多 Agent 并行子任务可独立、合并边界明确能并行探索或实现独立模块共享文件竞争、集成失败、重复上下文与额外费用

什么时候不要并行

两名 Agent 同时改一份 feature_list.json 和同一工作区，会出现覆盖或重复领取。先拆独立工作区、独立任务与证据，再由单一集成者合并和复测。若 F03 必须先改 F02 的数据模型，平行实现很可能先增加合并工作。原文没有证明多 Agent 优于单 Agent，不应把“多代理”当作自然升级。

长期运行必须补成本和停止条件

示例的循环适合展示接续，不适合直接承担预算承诺。更强设计需区分临时网络故障、权限拒绝、需求冲突、测试失败和无法判定的外部状态。只有契约允许的临时故障进入有上限重试；权限拒绝不能通过换工具或扩大凭据来“恢复”。同一失败连续重复且没有新证据时停止，报告事实。

费用预算、墙钟时间和最大尝试次数应是程序可执行的限制。只在提示里写“节约 token”不能限制一个无上限循环。要给收尾和保存证据留资源，额度耗尽前保存未完成状态；不要因接近上限而把功能批量标为通过。

信任边界与数据最小化

编码 Agent 需要的权限不应包含正式部署、生产设备或消息发送。测试账号、样本和日志使用隔离数据。进度文件记录“该去哪个受控位置查证”，而不是复制凭据、真实设备标识、用户音频或会话令牌。导入的 issue、网页和工具结果不拥有改变需求或触发外部操作的权力。

15 · 评估进展，不用 passes 数量冒充可靠性

源码事实 progress.py 的 count_passing_tests 读取 JSON，按 test.get("passes", False) 的真值计数，再打印比例。它没有执行步骤、检查证据或严格校验布尔 schema。JSON 解析或读取失败时返回 0,0。该数字是文件中声称通过的比例，不是独立测试系统测得的成功率。[10]

教学评估方案 若要证明自己的改造有效，应固定任务规格、模型版本、工具权限、初始代码与环境，对比“只有高层提示”和“交接方案”。再单独比较加入结构校验或持久检查点后的变化。不要一次换模型、增预算、扩工具，再把所有收益归给进度日志。

指标明确定义避免的误读
需求通过率独立执行器实际通过的需求数 ÷ 固定版本应验需求总数；blocked 单列删除难项导致分母变小，或 Agent 自报 true 被计作实测
虚假完成数标记通过但独立复核未通过的项数；同时报告复核项数只展示漂亮通过率，却不说明抽核范围
恢复成功率指定故障点中，恢复后达到规定状态且未违反不变量的次数 ÷ 实际注入次数“进程又跑了”被当作恢复正确
重新定向成本每轮从启动到确认基线的时间、工具调用与模型用量只算写代码时间，遗漏重复探索与修复
有效交付成本总模型与工具费用、测试设备占用、人工审查时间 ÷ 验收通过的工作量只比较 token 单价，不计失败重试和审查
外部重复执行数同一业务意图实际创建的额外远端任务数本地只显示一条而掩盖远端重复

如何安排可复查的故障注入

在隔离环境中，分别选择“初始化清单写到一半”“测试前后”“代码与状态之间”“远端受理但客户端超时”“保存检查点前后”作为停止点。为每个停止点提前写出期望状态与禁止行为，再启动恢复。否则看到结果后再改成功定义，会失去评估意义。

同一配置需要多次独立运行，保留每次结果而不是只挑成功案例。报告样本数、失败类别和环境限制。若测试存在偶发失败，单列重试前后的结果，避免靠不断重跑把红灯变绿。本文没有运行该实验，因此不提供改善百分比、平均耗时或费用估计。

任务台的可检验验收提案

  1. 初始化中断后，不因 feature 文件存在就自动放行编码；记录缺失材料。
  2. 改写需求描述但保留 passes 的提交被结构守卫拒绝；获批规格变更走另一条可追踪流程。
  3. 没有对应修订的测试记录时，不能把 F02 标为已验证。
  4. 同一 req-17 重复发送后，隔离远端仅有一个关联任务；主动“再建一个”分配新意图。
  5. 远端结果无法查询或去重过期时，状态是 blocked 或 unknown，而不是失败后自动重发。
  6. 恢复后先验证基线，不能直接执行日志里遗留的有副作用命令。
  7. 最后输出逐项结果、未覆盖范围与未决操作；不把演示成功写成已获准生产发布。

这些是建议的验收规格，不是本讲义已完成的测试报告。实现它们需要执行器、隔离环境与服务配合；仅修改提示词无法全部实现。

16 · 给 OEM 程序员的一次设计评审

教学推导 回到设备回归任务台。你可以保留文章最有用的基本结构，再按风险决定补强顺序。不是先搭一个大平台，而是先回答几个会影响正确性的具体问题。

第一步，限定 Agent 产出的责任

若 Agent 只写代码，由人运行隔离测试和合入，主要风险是需求遗漏、交接不清与伪通过。优先建立稳定需求表、单功能增量、进度记录和独立复核。先不让它直接操作设备或远端执行服务。

第二步，把“能跑”与“通过”拆开

init.sh 的成功表示环境启动条件满足。F02 通过表示规定用户链路在指定版本、指定环境里成立。一次干净 Git 提交表示代码版本可定位。它们是三个事实。设计评审时，要求每个“完成”字段只代表其中一种，不允许一个绿色图标替代所有状态。

第三步，接入远端前明确未知结果

为创建任务定义业务意图标识、查询接口与去重期。若执行服务不提供足够契约，就不要在 Agent 循环中启用自动创建与重试。可以先让 Agent 生成待审核任务描述，由受控执行器执行。这样牺牲一些自动化程度，换来明确的权限和状态边界。

第四步，确定恢复优先级

恢复先保全现场，再核对版本和规格；然后处理未决外部操作，重建环境并做基线复测，最后才领取新功能。代码和数据不兼容时不要自动回退，需求冲突时不要自动改要求。对账失败时，交出“因何阻塞、缺哪项证据”就是正确的工程结果。

带进评审会的七个问题

  • 需求表由谁批准，编码 Agent 能不能悄悄改掉验收步骤？
  • passes 由谁写，背后对应哪次真实运行和哪个代码版本？
  • 启动脚本重复执行会不会重置数据或启动错误版本？
  • 进程在任意两步之间退出，会留下哪些不一致材料？
  • 远端已执行但响应丢失时，凭什么区分重试与新意图？
  • 自动循环何时停止，谁承担测试资源、费用与副作用？
  • 哪些结论只在 Web 假环境成立，哪些已经在目标手机与真实测试链路验证？

文章值得采用的是明确范围、增量推进和可接续交接。需要自行补齐的是强制验收、持久状态与外部副作用恢复。把这两部分分清，才能知道自己现在是在复用一套开发经验，还是已经为长期运行建立了可检验的协议。
